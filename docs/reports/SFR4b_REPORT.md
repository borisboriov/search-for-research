# Аудит безопасности: что проверяется, чем и как читать красный job

Итерация SFR-4b (05.09.2026), спека `docs/specs/SPEC_SFR4b_security_ci.md`; до 05.09 файл назывался `SECURITY_CI.md`. Слой
автоматических проверок поверх ревью: уязвимые зависимости, известные
небезопасные паттерны, секреты, проблемы образов. Всё — открытые инструменты,
**ни одного платного механизма GitHub, ни одного SaaS-аккаунта и ни одного
токена**. CodeQL/Advanced Security на приватном репозитории платные и потому
не используются; их роль частично закрывает semgrep с вендоренными правилами.

Одна команда локально:

```bash
make audit                                   # всё, включая собранные образы
make audit AUDIT_ARGS="--no-images"          # как в CI
make audit AUDIT_ARGS="--fail-unfixed"       # строго: валить и CVE без фикса
```

Драйвер — `scripts/audit.py`. Он печатает команды, которые запускает: любой
шаг можно повторить руками и посмотреть полный вывод.

## Инструменты

| Слой | Инструмент | Версия | Что покрывает |
|---|---|---|---|
| Зависимости Python | `pip-audit` | 2.10.1 | известные CVE по залоченным версиям (`uv.lock`), отдельно рантайм и dev+security |
| Зависимости Node | `npm audit --audit-level=high` | из npm | известные CVE в `apps/web` |
| Код Python | `bandit -r packages apps/api -ll` | 1.9.4 | небезопасные паттерны (subprocess, yaml.load, хардкод креденшелов) |
| Код Python + TS + Dockerfile | `semgrep` с правилами из `security/semgrep/` | 1.176.1, 236 правил | паттерны безопасности; паки `p/python`, `p/typescript`, `p/docker`, `p/react` |
| Секреты | `gitleaks` — рабочее дерево и **вся история** | v8.30.1 | ключи и токены в коде и в коммитах |
| Файловая система | `trivy fs` | 0.74.0 | CVE по lock-файлам + мисконфиги Dockerfile |
| Образы | `trivy image` (только локально) | 0.74.0 | CVE базовых образов и бинарей внутри |
| Dockerfile | `hadolint` | v2.15.1 | лучшие практики |

**Где живут инструменты.** Питоновские — в uv-группе `security`
(`pyproject.toml`, версии запинены точно через `==`); группа не входит в
`default-groups`, поэтому `make test` и job `checks` её не ставят. Бинарные
(gitleaks, trivy, hadolint) `make audit` ищет **сначала в PATH, потом в
запиненном docker-образе**; нет ни того ни другого — шаг помечается `SKIP` с
объяснением и прогон не падает. В CI бинарники ставятся с релизов GitHub и
`SKIP` считается падением (флаг `--strict`).

**Почему правила semgrep вендорены.** `--config p/python` тянет правила с
`semgrep.dev` на каждом прогоне: набор не версионируется (сегодня одни
правила, завтра другие), и CI зависит от внешнего сервиса. Паки выгружены в
`security/semgrep/` скриптом `fetch-rules.sh`; там же `MANIFEST.txt` с датой,
числом правил и sha256 каждого файла. Обновление правил — осознанный шаг:
запустить скрипт, посмотреть diff, прогнать `make audit`, разобрать новые
находки.

Два пака из спеки в наборе отсутствуют, оба — с причиной:

- **`p/nextjs`** реестр отдаёт **пустым** (`rules: []`, 0 правил); вместо него
  взят `p/react` (4 правила).
- **`p/secrets`** убран после первой же попытки пуша: файл правил целиком
  состоит из секрето-подобных строк — регулярок и плейсхолдеров вида
  slack-вебхука `hooks.slack.com/services/T…/B…/…`. GitHub Push Protection отклонила
  пуш, указав на строку 618 этого файла, и наш собственный gitleaks помечал
  его как утечку. Держать в репозитории файл, который нельзя запушить, нельзя;
  прятать его исключением в gitleaks — значит откладывать ту же проблему до
  следующего пуша. Слой секретов и без него закрыт дважды: gitleaks (рабочее
  дерево и вся история, ~200 правил) и сама Push Protection на стороне
  GitHub — то есть покрытие не потеряно, убрано дублирование.

## Политика: что валит прогон

- **High/Critical — падение.** Medium/Low печатаются, но не валят.
- **CVE без доступного фикса не валят.** Если у уязвимости нет `FixedVersion`,
  чинить её нечем, кроме ожидания апстрима, и красный job каждый день
  превращается в шум, который перестают читать. Такие находки идут в строку
  `WARN` с количеством. Строгий режим — `--fail-unfixed`.
- **CVE с доступным фиксом — падение всегда**, включая базовые образы: там
  «фикс есть» означает «пересобери образ» или «подними версию».
- semgrep: `ERROR` — падение, `WARNING`/`INFO` — строки в логе.
- hadolint: `error` — падение, `warning`/`info` — строки в логе.

## Allowlist: где и как в него попадать

Правило спеки: **никаких «выключить правило целиком»**. Исключается конкретный
путь или конкретная строка, рядом — причина и условие пересмотра.

| Инструмент | Файл | Как исключить |
|---|---|---|
| gitleaks | `.gitleaks.toml` | блок `[[allowlists]]` с `description` и `paths`/`regexes` |
| semgrep | комментарий в коде | `# nosemgrep: <rule-id>` + причина рядом (файл `.semgrepignore` **не заводить**: он заменяет собой набор умолчаний, а не дополняет его) |
| bandit | комментарий в коде | `# nosec BXXX` + причина |
| pip-audit | `scripts/audit.py` | `--ignore-vuln <GHSA/CVE>` в команде шага, с комментарием |
| trivy | `.trivyignore.yaml` в корне | запись с `id`, `paths`, `statement` и `expired_at` (дата пересмотра) |
| hadolint | комментарий в Dockerfile | `# hadolint ignore=DLxxxx` **непосредственно** над инструкцией, объяснение — строкой выше |

На 05.09.2026 в allowlist только два вида записей, оба — не про наш код:

1. `.gitleaks.toml`: каталоги вне git (`.venv`, `node_modules`, `data`,
   `.next`, кэши) — `gitleaks dir` идёт по файловой системе и не знает про
   `.gitignore`; там 13 находок первого прогона, все в чужом коде.
   Исключения для `security/semgrep/*.yaml` намеренно **нет**: две оставшиеся
   находки (`slack-webhook-url`, `private-key`) были в паке `p/secrets`, и он
   убран из вендоринга целиком — прятать их исключением значило бы получить
   отказ Push Protection на пуше вместо красного `make audit` на машине.
2. Инлайн `# hadolint ignore=`: DL3008 (не пинуем версии apt — Debian вымывает
   старые версии, пин ломает сборку через месяц) и DL3066 ×3 (имя пользователя
   вместо uid; uid зафиксирован соседней строкой `useradd`/`adduser`).

Ни одной уязвимости в allowlist нет.

### Что именно исправлено

- **trivy fs, DS-0002 (HIGH):** `deploy/proxy/Dockerfile` не задавал `USER` —
  Caddy работал от root. Это единственный контейнер, смотрящий в интернет
  (api и web обезроутили ещё в SFR-4). Добавлены пользователь `caddy`
  (uid 10001), `setcap cap_net_bind_service` на бинарь (иначе не занять
  80/443) и владение `/data` и `/config`. Проверено: `make deploy-local`
  поднимается, `docker exec sfr-proxy id` → uid 10001, access-лог пишется,
  rate limiting работает (10×200, затем 429), e2e 18/18.
- **trivy image `sfr-proxy`, 23 HIGH в пакетах Alpine** (curl, c-ares,
  openssl) — все с доступным фиксом: образ `caddy` пересобирается реже, чем
  выходят патчи. Добавлен `apk upgrade --no-cache` в рантайм-стадию.
- **trivy image `sfr-proxy`, 5 HIGH/CRITICAL в самом бинаре Caddy**
  (`golang.org/x/crypto` CVE-2026-56854 CRITICAL, `x/net`, `x/text`, `grpc`):
  фиксы в библиотеках вышли, Caddy 2.11.4 их ещё не подтянул. Бинарь мы
  собираем сами через xcaddy, поэтому версии подняты директивами `--replace`
  в `deploy/proxy/Dockerfile`. Проверено: `caddy version` → v2.11.4, модуль
  `http.handlers.rate_limit` на месте, trivy → 0 находок.
- **trivy image `sfr-web`, 4 HIGH** (`brace-expansion` ×2, `ip-address`,
  `tar`) — все в связке npm, встроенной в `node:24-slim`. В рантайме
  запускается `node server.js`, npm не нужен: удалён вместе с corepack.
- **hadolint DL3025:** `HEALTHCHECK` в `apps/api/Dockerfile` был в
  shell-форме. Переведён в exec-форму; `|| exit 1` убран как лишний —
  `curl -f` и так возвращает ненулевой код на 4xx/5xx.

### Что осталось и почему

**119 HIGH/CRITICAL в базовых образах `sfr-api` (63, Debian 13.6) и `sfr-web`
(56, Debian 12.15)** — все со статусом `affected`/`fix_deferred`/
`will_not_fix`: исправленной версии пакета в Debian нет. Сделать с ними
нечего, кроме двух вещей, и обе уже делаются:

- образы пересобираются на каждом деплое (`docker compose up -d --build`),
  так что патч попадает на сервер в первую же выкладку после выхода;
- еженедельный cron job `security` покажет, когда фикс появится: находка
  перейдёт из «без фикса» в «фикс есть» и job станет красным.

Оговорка честности: **эксплуатируемость каждой из 119 не проверялась**.
Это CVE пакетов базового образа (systemd, glibc, perl, util-linux), большая
часть которых требует локального доступа к контейнеру. Утверждение «сервис
уязвим 119 способами» из этой строки не следует, как не следует и обратное.

## Что CI не проверяет

- **Образы.** Job `security` гоняет `trivy fs`, но не `trivy image`: чтобы
  просканировать образы, их надо собрать, а сборка `sfr-api` — это скачивание
  torch и весов FRIDA, десятки минут на каждый прогон. CVE базовых образов
  ловятся локальным `make audit` (он сканирует уже собранные образы) и
  пересборкой на деплое. Это осознанный разрыв, а не недосмотр.
- **Живое поведение.** Rate limiting, заголовки, недоступность API снаружи —
  это `make deploy-local` + e2e, не сканеры.
- **Логика приложения.** Сканеры ищут известные паттерны; ошибки в бизнес-логике
  (что показывать при слабом совпадении, кэшируется ли сбой) ловит только
  ревью и тесты.

## CI: job `security`

`.github/workflows/security.yml` — отдельный workflow, а не job в `ci.yml`:
расписание живёт вместе с проверками, которым оно нужно, и красный аудит не
путается с красными тестами в списке проверок PR.

- **Когда:** push в `main`, pull request, **еженедельный cron** (понедельник,
  04:17 UTC) и ручной запуск (`workflow_dispatch`). Cron нужен потому, что
  новые CVE появляются без изменений кода.
- **Права:** `contents: read`. Секретов не требуется вообще.
- **Сканеры:** ставятся с релизов GitHub по запиненной версии **и проверяются
  по sha256** — вместо сторонних actions (лишний поставщик кода в CI; часть,
  например gitleaks-action, для организаций требует лицензионный ключ).
- **Чекаут с `fetch-depth: 0`** — иначе gitleaks не увидит историю.

### Обновление версии инструмента

1. Питоновские: поднять `==`-пин в группе `security` в `pyproject.toml`,
   `uv lock`.
2. Бинарные: поднять версию в `.github/workflows/security.yml` **и в
   `DOCKER_IMAGES` в `scripts/audit.py`** (две точки, легко разойтись),
   пересчитать sha256:
   ```bash
   curl -sSfL -o /tmp/x <url> && shasum -a 256 /tmp/x
   ```
3. Правила semgrep: `bash security/semgrep/fetch-rules.sh`, посмотреть diff.
4. Прогнать `make audit`, разобрать новые находки, обновить таблицу выше.

## pre-commit

`gitleaks` на staged-изменениях — `security/gitleaks-precommit.sh`, хук
`gitleaks` в `.pre-commit-config.yaml`. Он берёт бинарь из PATH, иначе
запускает запиненный docker-образ, а если нет ни того ни другого — печатает
предупреждение и **пропускает** (блокировать коммит нечем, но молчать нельзя).

Официальный хук gitleaks собирается из исходников (`language: golang`) — на
машине без Go это долгая сборка при каждом `pre-commit install`; локальный
скрипт делает то же за полсекунды.

Тяжёлые сканеры (semgrep, trivy) в pre-commit сознательно не ставятся: хук
должен быть секунды, а не минуты. Их место — `make audit` и CI.

Хук проверен подложенным секретом: реальный по виду AWS-ключ ловится
(`leaks found: 2`, коммит не проходит). Осторожно с проверкой на канонических
примерах из документации — канонический AWS-ключ вида `AKIA…EXAMPLE` входит
в allowlist самого gitleaks и проходит; это не поломка хука.

## Как читать красный job

1. Внизу лога — сводная таблица со статусом каждого шага и строка
   `Падение: <шаги>`.
2. Найти шаг выше по логу: перед каждым напечатана команда, которой он
   запускается. Повторить её локально.
3. Дальше — по типу находки:
   - **зависимость с фиксом** → поднять версию (`uv lock --upgrade-package X`
     или `npm update X`), прогнать `make audit`;
   - **CVE базового образа с фиксом** → пересобрать образ
     (`docker build --pull`), при необходимости поднять тег базового образа;
   - **semgrep/bandit** → это код: либо чинить, либо, если ложное срабатывание,
     `# nosemgrep`/`# nosec` с причиной **в той же строке кода**;
   - **gitleaks** → считать секрет скомпрометированным и **ротировать** его;
     чистка истории — вторична и делается только по решению Бориса;
   - **уязвимость без фикса, которая мешает** → `.trivyignore.yaml` с
     `statement` и `expired_at`, но сначала ответить себе, почему ждать нельзя.
4. Прогон, который упал на `SKIP` в CI, — это дефект job'а (инструмент не
   поставился), а не находка.

## Definition of Done (честно)

Чеклист §4 `docs/specs/SPEC_SFR4b_security_ci.md`.

- [x] **`make audit` зелёный локально на текущем main.** Проверено в обоих
      режимах: полном (с образами) и `--no-images --strict`, то есть ровно
      том, который гоняет CI. В allowlist нет ни одной уязвимости — только
      пути (каталоги вне git, вендоренные правила) и три инлайн-исключения
      hadolint с причинами.
- [~] **CI job `security` добавлен, версии запинены, cron еженедельный.**
      Написан и проверен настолько, насколько это возможно без пуша: YAML
      разбирается, имена файлов внутри архивов релизов сверены (`gitleaks`,
      `trivy` лежат в корне архива), sha256 посчитаны с реально скачанных
      файлов, та же команда `make audit AUDIT_ARGS="--no-images --strict"`
      прогнана локально и зелёная. **Первый настоящий прогон — после пуша
      Бориса**; до него пункт нельзя считать закрытым. Токенов и платных
      возможностей job не требует: права `contents: read`, сканеры — с
      открытых релизов.
- [x] **`gitleaks` в pre-commit; история проверена.** Хук ловит подложенный
      ключ. История — 78 коммитов, `--all --full-history`, **секретов нет**;
      инструкция по ротации в TODO_BORIS не понадобилась.
- [x] **Реальные находки исправлены, регрессии зелёные.** `make lint`,
      `make typecheck`, `make test` (204 теста, покрытие 95.65%),
      `make web-lint/typecheck/test/build`, `make eval` (≡ SFR-2: Success@k,
      nDCG и MRR совпали с `docs/SFR2_REPORT.md`; разошлась только строка
      латентности — замер шёл на нагруженной машине, поэтому сгенерированный
      отчёт откачен).
- [x] **`docs/SFR4b_REPORT.md`; DECISIONS, SESSIONS, TODO_BORIS обновлены;**
      в `.claude/agents/sfr-reviewer.md` добавлена строка чеклиста
      «`make audit` зелёный» (файл вне git, правится локально).

### Что не дотянуто

1. **Отдельных тестов на исправления нет.** Все находки оказались в
   Dockerfile и слоях образов — питоновский и TS-код не менялся вовсе, а
   юнит-тест на «прокси работает не от root» — это и есть запуск компоновки.
   Проверка сделана прогоном: `make deploy-local`, `docker exec sfr-proxy id`,
   шторм на rate limiting, e2e 18/18 против компоновки.
2. **Ветка привилегированных портов не проверена.** Локальная репетиция
   слушает 8080, `cap_net_bind_service` в ней не задействована. Первый боевой
   запуск — единственная настоящая проверка; пункт заведён в TODO_BORIS и в
   `deploy/README.md`.
3. **Эксплуатируемость 119 CVE базовых образов не разбиралась** — только
   статус «фикса нет». См. «Что осталось и почему».
4. **`p/nextjs` пуст в реестре** — специфичных для Next.js правил в наборе
   фактически нет; `p/react` (4 правила) закрывает только базовые случаи
   вроде `dangerouslySetInnerHTML`. Прокси-роут и SSR-логику по-прежнему
   проверяет только ревью.
5. **`p/secrets` не вендорится** (см. выше). Дублирующий слой у semgrep убран,
   слой как таковой остался за gitleaks и Push Protection — но если semgrep
   когда-нибудь понадобится как единственный сканер секретов, эту дыру надо
   помнить.

## Ограничения

- **Сканеры не ходят офлайн полностью.** Правила semgrep вендорены, версии
  инструментов запинены, но базы уязвимостей по определению внешние: pip-audit
  спрашивает PyPI/OSV, npm audit — реестр npm, trivy качает свою БД. Аккаунтов
  и токенов это не требует.
- **Базовая линия «ноль находок» — это про сегодняшнюю дату**, а не про
