# SFR-5b: Каталог без квоты — эксперимент для решения о расширении базы НР

**Код итерации:** `SFR-5b` (мини-итерация к SFR-5, как SFR-4b к SFR-4; SFR-7 «Ранжирование» не переименовывается и не сдвигается). Ветка `sfr-5b` от `main`, отчёт `docs/SFR5b_REPORT.md`.
**Контекст:** каталог 12 вузов / 5 538 профилей собран **квотой**: из 12 675 авторов, прошедших эвристику НР (≥10 работ, h ≥5, публикация за 3 года), квота взяла 5 816 — **6 859 человек (54%) отрезаны не данными, а нашим лимитом** (`docs/SFR5_REPORT.md` §1). Борис решает, как расширять базу НР (issue `decision` #90). Вариантов несколько (снять квоту в тех же вузах · добавить вузы и НИИ · мягче пороги · ORCID · РНФ/ЕГИСУ · C6 · договоры с eLibrary/КиберЛенинкой); первый — самый дешёвый, потому что пулы всех 12 вузов уже лежат в `data/raw` (109 страниц, 16 870 уникальных авторов) и не стоят ни одного запроса. Чего мы не знаем — **что станет с качеством поиска, когда каталог вырастет вдвое при том же составе вузов**. При росте ×10 (535 → 5 538) Success@5 уже просел со 100% до 90,9%. Эта итерация даёт цифры для решения, **прод не трогает**.
**Прочитай перед стартом:** `CLAUDE.md`; `docs/DECISIONS.md` (сводка действующих решений + записи 05–06.09 про квоту OpenAlex, отбор квотой, склейку, пороги); `docs/SFR5_REPORT.md` (§1 состав, §3 время прогона, §5 пороги, §10 что не дотянуто); `packages/sfr-match/eval/README.md`; последняя запись `docs/SESSIONS.md`; `docs/sfr5b_pool_census.json` (перепись пулов, собрана 17.09 продуктовым тредом — §7).
**Режим:** автономный. Решения — в `docs/DECISIONS.md`. Только OpenAlex; никакого eLibrary и скрейпинга сайтов. Ключ OpenAlex берётся клиентом из settings — **в командной строке и в транскрипте ключ не появляется** (`curl` с `api_key=` не использовать; для любых запросов к API — `OpenAlexClient` или существующие CLI/скрипты).

## 1. Скоуп

Делаем: (а) каталог **тех же 12 вузов без квоты** в отдельной БД; докачка работ ключом; дедупликация; профили; экспорт; (б) индекс FRIDA `data/indexes_sfr5b`; (в) регрессия качества на golden/OOD/external и **метрики для решения** (§6); (г) калибровка порогов нового индекса; (д) отчёт с честным DoD, файл-предложение, issues.

## 3. Каталог без квоты

1. **Отбор.** Для каждого из 12 вузов (ID — из таблицы `institutions` копии БД, не хардкодить): `SFR_DB_URL=… uv run sfr etl authors --institution <id> --strategy stratified --quota 100000 --keep-existing`. Квота ≥ размера пула → `allocate_quota` возвращает все области целиком (см. `catalog.py`), то есть берутся **все годные** — стратификация вырождается в «без квоты», код менять не нужно. Пулы читаются из кэша (проверь `network=0` в `data/run_stats.json`; если пошла сеть — остановись и разберись: значит, изменились params запроса). Ожидание: кандидатов ≈ 12 675 до учёта двойных аффилиаций и склеек (SFR-5 §1: 265 человек в двух пулах, правило «первый вуз из списка» — `docs/DECISIONS.md` 05.09).
2. **Работы — только через прогрев.** `SFR_DB_URL=… uv run python scripts/warm_works_cache.py` (по умолчанию `--workers 6 --rps-per-worker 1.2`, общий колпак 10 rps). Ожидание: ~6 900 авторов к прогреву → **~13 800 запросов**, а дневная квота ключа — 10 000; она сбрасывается в **00:00 UTC = 03:00 МСК**. Скрипт останавливается на первом 429 (это его контракт, не ошибка): дождись 03:01 МСК и запусти снова — он продолжит с места остановки по кэшу. На время ожидания — офлайн-шаги (Makefile, скрипт метрик §6, скелет отчёта). Если 429 пришёл раньше 10 000 запросов — бюджет дня частично потрачен, план тот же. Запросы и время — в §3 отчёта, как в SFR-5.
3. **Запись из кэша:** `SFR_DB_URL=… uv run sfr etl works --only-missing` (network должен быть 0). Затем `make catalog-sfr5b` (backfill-mega → dedup → build-profiles → export), см. §4 про dedup.
4. **Однородность корпуса — обязательна.** Если к **04:30 МСК** работы загружены не у всех кандидатов (квота не хватила, сеть), индекс на смешанном корпусе **не собирать** — урок SFR-5: профили с полными текстами занимали 46–50% топ-5 при доле 9,6%. Вместо этого в БД эксперимента снять флаг `is_supervisor_candidate` у кандидатов без работ (одним SQL-UPDATE, только в `sfr5b.db`; число снятых — в отчёт) и продолжать на однородном подмножестве, честно назвав его размер.

## 4. Дедупликация

`SFR_DB_URL=… uv run sfr etl dedup --dry-run --review-out packages/sfr-match/eval/dedup_for_review_sfr5b.md`, посмотреть, затем `--apply` с тем же `--review-out`. Ожидание: склеек станет заметно больше 18 — сигнал «общая работа» теперь доступен у 100% профилей, а не у 533; плюс среди 6,9 тыс. новых людей есть дубли к старым. В отчёт: склеек по типам сигнала, групп тёзок оставлено, `suspect_merge` (было 143), выжили ли 3 профиля превью лендинга и id из `judgments.jsonl` (сколько судейских пар указывают на автора, который стал дублем — таким парам оценка не пропадает, но их надо учесть при подсчёте метрик).

## 6. Качество и метрики для решения

Базовая линия — SFR-5 на 5 538: Success@5 / Success@1 = 90,9% / 77,3% на неизменном наборе из 22 запросов, 91,7% / 75,0% на 24; мягкий Success@5 = 100% (`docs/SFR5_REPORT.md` §4). Все сравнения — **только по этим наборам и только Success@5/@1**; nDCG между отчётами не сравнивать (пул судейства разный).

1. `make eval-sfr5b`: golden → `runs_sfr5b`, OOD → `runs_ood_sfr5b`, external → `runs_external_sfr5b`; судейские пулы `pool_sfr5b.jsonl`, `pool_ood_sfr5b.jsonl`.
2. **Судейство новых пар** по рубрике SFR-1 (grade 2 = покрыто главное содержание запроса), дописать в `judgments.jsonl` с полем `iteration: "SFR-5b"`; `sfr-match review-sample --iteration SFR-5b --out packages/sfr-match/eval/judgments_for_review_sfr5b.md` (20 пар на проверку человеком). Неоценённые пары считаются 0 — это пессимистичная оценка, так и написать.
3. **Таблица «5 538 → N»**: Success@5/@1 на наборах 22 и 24, мягкий Success@5, внешний запрос(ы) — куда попали, OOD: сколько посторонних запросов на большом корпусе нашли настоящего специалиста (процедура подтверждения из SFR-2 — контрольный перефраз; на это не больше 30 минут, непроверенные так и пометить).
4. **Метрики для решения** — маленький скрипт `scripts/sfr5b_decision_metrics.py` (логика функцией с юнит-тестом, вход — `runs_sfr5` vs `runs_sfr5b` + `judgments.jsonl` + оба `profiles_*.jsonl`; выход — `docs/sfr5b_decision_metrics.json` и таблица в отчёт):
   - **coverage gain**: доля запросов (golden 24 + external), у которых в топ-5 появился хотя бы один **новый** НР (нет в `profiles_sfr5.jsonl`), и доля, где новый НР оценён grade 2; отдельно — доля запросов, где **топ-1 стал новым**;
   - **displacement**: сколько старых grade-2 НР вылетели из топ-5 и кем заменены — новым grade 2 (нейтрально/хорошо), новым grade ≤1 (плохо — это и есть «разбавление»), старым;
   - **разнообразие организаций**: число различных вузов в объединении топ-10 по всем запросам (было/стало) и распределение вузов в топ-5 (не стал ли один вуз доминировать);
   - **сдвиг шкалы**: медиана top-1 score по golden и по OOD было/стало.
5. Латентность (необязательно, если остаётся время): `SFR_API_INDEX_ROOT=data/indexes_sfr5b SFR_API_CARDS_PATH=data/exports/cards_sfr5b.jsonl make api` + `uv run python scripts/bench_api.py --models frida --no-docker --out docs/sfr5b_resources.json`; ожидание — p50 около прежних ~130 мс (время держит инференс, не скан).
