# SFR-3: Фронтенд (Next.js) — лендинг, результаты, открытая страница НР

**Контекст:** SFR-0 — данные (535 профилей МФТИ+МГУ), SFR-1 — модель FRIDA, SFR-2 — API (`apps/api`: `POST /api/match`, `GET /api/supervisors/{id}`, `GET /api/health`), порог 0.27. Эта итерация — веб-приложение поверх готового API. Прочитай перед стартом: `docs/NEXT.md` (§1 и «не переоткрывать» — обязательны), `apps/api/src/sfr_api/schemas.py` (контракт), `docs/SFR2_REPORT.md` (латентность), `TODO_BORIS.md`, последняя запись `docs/SESSIONS.md`.
**Дизайн готов и является источником истины по внешнему виду:** `apps/web/design/` — `DESIGN_HANDOFF.md` (читать первым), `DESIGN_SYSTEM.md` (§1 токены → `globals.css`/`tailwind.config`), `mockups/*.dc.html` (точные значения px/hex/gap — брать как есть, не округлять к сетке и не менять шрифты), `mockups/*.png` (сверка глазами), `logo/*.svg`. Открытые вопросы handoff решены: ссылку «Научрукам» в шапке и аватар пользователя **убрать** до пилота.
**Режим:** автономный. Решения — в `docs/DECISIONS.md`.

## 1. Скоуп

Делаем: `apps/web` — Next.js (App Router, TypeScript) + Tailwind + shadcn/ui; три страницы по макетам (десктоп 1440 и мобайл 390); все состояния (skeleton, empty, ошибка сети); SEO-контур для открытых страниц НР (SSR, sitemap, метатеги); минимальные дополнения API, без которых фронт не собрать (§4); тесты; интеграция в Makefile/CI; отчёт.
НЕ делаем: авторизацию, ЛК, отзывы, отправку писем из сервиса (только показ email + шаблон + «Скопировать»), RAG-объяснения, C6/позиции НР, тёмную тему, rate limiting/кэш/деплой (это SFR-4), новые вузы, правки модели и индекса.

## 2. Страницы и поведение

- **`/` лендинг** — по `landing.dc.html` / `landing-mobile`: шапка с `Logo`, hero с `SearchBox` (textarea 3–500 симв., плейсхолдер-пример, CTA «Подобрать научрука», подпись «Бесплатно · без регистрации»), превью подборки из 3 карточек (на мобайле 2; данные превью — реальные, три заранее выбранных профиля из каталога, не вымышленные образцы из макета), «Три шага», полоса цифр (цифры — из `/api/health`: число профилей; вузов — 2; формулировки по макету, но без выдуманных чисел), CTA-секция, футер (`Logo` mono, подпись про OpenAlex). Сабмит → `/results?q=…`.
- **`/results?q=`** — по `results` / `results-mobile` / `results-empty`: `QueryBar` (запрос виден и редактируем), `FilterChip`-ы (вуз, h-index, должность) и сортировка по совпадению — фильтрация **клиентская** над ответом `/match` (k=10); счётчик «Найдено N · M вуза»; список `SupervisorCard` (десктоп горизонтальная с кнопкой «Открыть профиль», мобайл вертикальная кликабельная); skeleton-карточки на время запроса (p50 0,6 с, до 2 с под нагрузкой — индикатор обязателен); один reveal (fade + 8px, 200 мс), других анимаций нет. При `below_threshold: true` — `EmptyResults` по `results-empty` (заголовок, объяснение, 3 примера удачных запросов — взять из `packages/sfr-match/eval/queries.jsonl`, in-domain, кнопка «Изменить запрос»). Serendipity: фронт умеет рисовать состояние карточки по флагу `serendipity` из API; API пока флаг не выставляет (см. §4) — на реальных данных слот не показывается, в тестах и Storybook-подобной странице состояний — показывается. `robots: noindex` для `/results`.
- **`/supervisor/[id]`** — по `supervisor` / `supervisor-mobile`: `SupervisorHeader` (аватар-инициалы, ФИО, вуз · должность, чипы тем; блок «NN% совпадение» показывать только если пришли с результатов — через query-параметр `score`, иначе блок скрыт), две колонки: «Чем занимается» (короткий текст из `profile_text`/тем) + `WorksList` (**названия работ — в первую очередь**, год; аннотация — свёрнуто/вторично: эксперимент SFR-2 показал, что сигнал в названиях), «Наукометрия» (`MetricsCard`: h-index / публикации / цитирования, Tooltip «по данным OpenAlex»), `ContactCard` (email если есть в данных, иначе «email не найден в открытых источниках» + шаблон письма + «Скопировать письмо»; шаблон — один, формальный, из паспорта БФТ 2.2, с автоподстановкой имени НР), `ClaimProfileLink` («Это вы? Редактировать или скрыть профиль» → `mailto:` с темой, содержащей `author_id`; форма — пилот). Мобайл — порядок блоков по макету. **SSR обязателен**: HTML содержит имя, вуз, темы и `<title>`/`description` до гидратации.
- **Ошибка сети / API недоступен** — состояние в стиле `results-empty`: заголовок, одна фраза, «Повторить». Пустой/битый `id` → 404-страница в том же стиле.
- Общее: тап-таргеты ≥44px; брейкпоинты стандартные Tailwind (макеты 1440/390, промежуточные — по здравому смыслу: 3→1 колонки, две колонки профиля → одна на `< lg`); шрифты через `next/font/google` (Spectral 500/600, Golos Text 400/500/600); иконки lucide-react.

## 3. SEO-контур (требование, не пожелание — спека MVP v1.6, NEXT.md §1)

- `/supervisor/[id]` рендерится на сервере; `<title>` = «{ФИО} — {вуз} | Search for Research», description из тем и должности; канонический URL; Open Graph базовый.
- `sitemap.xml` по всем профилям каталога (генерируется на сервере из API, см. §4), `robots.txt` (разрешить всё, кроме `/results` и `/api`).
- Страницы НР кэшировать (ISR/revalidate ≥ 1 час или статическая генерация при билде — выбери и обоснуй в DECISIONS; каталог меняется раз в семестр).
- Проверка: `curl` без JS отдаёт полный HTML профиля; sitemap содержит все 535 URL; Lighthouse SEO ≥ 90 на странице НР.

## 4. Минимальные дополнения API (`apps/api`, без изменения логики поиска)

- `GET /api/supervisors?limit=&cursor=` (или `GET /api/supervisors/ids`) — постраничный список `author_id` + имя + вуз для sitemap и превью лендинга.
- В `SupervisorCard`-схему ответа: опциональные `serendipity: bool = false`, `position: str | null` (должность, если есть в данных), `email: str | null` (если есть в данных; НЕ парсить ничего нового — только то, что уже в каталоге; нет — `null`), `cited_by_count`, `top_works: [{title, year}]` (5–10 свежих/цитируемых — из данных SFR-0). Тесты API дополнить.
- CORS: origin фронта из settings. Ничего больше в API не трогать.
