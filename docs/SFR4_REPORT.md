## 2. Серая зона порога и словесные грейды (§0.9, решение Бориса 05.09)

Мотивация: живой запрос «интересно computer science backend engineering» дал
top-1 = 0.34 и мусорную выдачу (физики/химики) **без предупреждения** — порог
0.27 калибровался на бытовых посторонних запросах (score ≤ 0.21), а
академически звучащие посторонние ложатся выше него.

Сделано:

- **API**: `SFR_API_SCORE_WEAK = 0.36` (между минимумом живых попаданий 0.31
  и их средним 0.43) и `SFR_API_SCORE_HIGH = 0.42` — в settings, отдаются в
  `/health`. Ответ `/match` несёт `confidence: none | weak | ok` (по top-1;
  `below_threshold` оставлен для совместимости) и `grade: high | medium | low`
  в каждом результате. Границы шкалы живут в одном месте — фронт чисел не знает.
- **Фронт**: при `weak` — баннер «Совпадения слабые — похоже, в базе пока нет
  специалистов по этой теме…» над выдачей, выдача остаётся; бейдж карточки —
  «высокое / среднее / слабое совпадение», процент — в tooltip
  («Косинусная близость с запросом: NN%»). `/dev/states` пополнен грейдами,
  баннером и QueryHint. Блок «NN% совпадение» на странице НР оставлен
  процентом — спека про него молчит, решение зафиксировано в DECISIONS.
- **Первый внешний запрос**: `e01` записан в
  `packages/sfr-match/eval/external_queries.jsonl` (`source: "boris"`).
  Прогон `sfr-match eval --queries external` по боевому индексу
  `frida_clean-535p-abe35971`: **top-1 = 0.337** (V. A. Knyaz, далее физики
  и химики) → при новых порогах попадает в **weak** (0.27 ≤ 0.337 < 0.36).
  Это же проверено e2e: на запросе e01 виден баннер и грейды «слабое
  совпадение» (`e2e/flow.spec.ts`).

Границы 0.36/0.42 — как и 0.27 — принадлежат паре модель×индекс
(`frida_clean`); SFR-5 перекалибрует все три на новом корпусе.

## 3. Компоновка и деплой

```
интернет ──443/80──> proxy (Caddy 2.11 + rate-limit, авто-TLS, gzip,
                     security-заголовки, JSON access-лог)
                        │ reverse_proxy
                        v
                     web (Next.js standalone, non-root node)
                        │ SFR_API_URL=http://api:8000 (SSR + прокси /api/match)
                        v
                     api (FastAPI + FRIDA, non-root app, Semaphore(2),
                     LRU-кэш /match, JSON-логи) ── порты наружу НЕ публикуются
тома: hf-cache (веса FRIDA), caddy-data/-config (TLS, access-лог)
монтируются read-only: data/indexes_sfr2, data/exports (cards.jsonl)
```

- Артефакты **доставляются, не собираются**: `deploy/sync-artifacts.sh`
  (rsync с чексуммами) возит индекс и `cards.jsonl`; веса FRIDA (~2 ГБ)
  скачивает первый старт контейнера в том — единожды.
- Процедуры «с нуля» и «обновление» — `deploy/README.md`. Выбранная схема
  сборки web: без живого API + обязательная пост-деплойная ревалидация
  `/` и `/sitemap.xml` (`POST /api/revalidate` с секретом). Причина: docker
  build не видит сеть compose. Важное свойство, пойманное на репетиции:
  **пересозданный контейнер web теряет рантайм-кэш ISR** и до ревалидации
  отдаёт билд-снапшот — поэтому ревалидация обязательна после каждого
  `docker compose up`, а не только после первого.
- Rate limiting: `/api/match` — burst 10/10 с + 30/мин с IP (для всех,
  включая ботов); страницы — 120/мин, статика `/_next/*` не считается,
  поисковые боты по UA — без лимитов. UA спуфится — осознанный компромисс
  пилота.
- Таймаут апстрима: `response_header_timeout 30s` на reverse_proxy —
  эквивалент `proxy_read_timeout` из спеки; зависший Next не держит
  соединения на прокси (15-секундный AbortSignal внутри Next покрывает
  только путь /api/match).

## 4. Локальная репетиция (`make deploy-local`)

- Стек поднимается одной командой; прокси на `http://localhost:8080` (без
  TLS — префикс http:// отключает auto-HTTPS; на бою тот же Caddyfile с
  доменом выпускает сертификат сам).
- **API снаружи compose недоступен**: `docker port sfr-api` пуст, порт 8000
  хоста не слушается контейнером (bench-проверка `api_port_8000_closed_from_host: true`).
- **e2e: 18/18 зелёные** против компоновки (`SFR_WEB_URL=http://localhost:8080
  make web-e2e`), включая новые тесты серой зоны и 404 витрины `/dev/states`
  в прод-сборке. Немедленный повторный прогон может упереться в burst-лимитер
  (10 POST за 10 с) — это лимитер работает, а не тест флакает; пауза в минуту
  решает.
- Пост-деплойная ревалидация проверена: sitemap 0 → 535 URL, счётчик и
  превью лендинга появляются.
- Репетиция поймала три реальных дефекта конфигурации до боя: лимитер
  считал статику; `handle` перехватывал запросы раньше `rate_limit`
  (лимит /api/match не работал вовсе); сброс ISR-кэша при пересоздании
  контейнера. Все три исправлены и перепроверены.

## 5. Перемер (§3) — локальный compose, Mac arm64, с пометкой

Полные данные: `docs/sfr4_bench.json` (скрипт `scripts/bench_sfr4.py`).
Латентность /match мерилась **мимо прокси** (изнутри compose-сети,
уникальные запросы — мимо кэша): через прокси лимитер честно отдаёт 429.

| Метрика | SFR-2 (контейнер, тот же Mac) | SFR-4 (компоновка) |
|---|---|---|
| /match p50 / p95, 1 поток | 577 / 760 мс | **201 / 254 мс** |
| /match p50 / p95, 4 потока | 1942 / 2439 мс | **753 / 976 мс** |
| Шторм 20 параллельных | не мерился (риск OOM — причина фикса) | 7×200 + 13×503 за 1.4 с, max 1.4 с, **без OOM** |
| RSS api в покое / после шторма | 3068 / 3209 МБ | 3090 / 3122 МБ |
| RSS web / proxy | — | 104 / 17 МБ |
| Холодный старт api (веса в кэше) | 24.0 с | 15.8 с |
| TTFB /supervisor/[id] холодный / из кэша | ~200 / 20 мс (SFR-3, next start) | 14.3 / 3.9 мс (через прокси) |

Разница p50 с SFR-2 (577 → 201 мс) — это не «стало быстрее от фиксов»:
другой прогон на той же машине при другой фоновой нагрузке; цифры обоих
столбцов — ориентиры одного порядка, а не бенчмарк-сравнение. Существенное
и воспроизводимое: 4 потока больше не дают ×3–4 деградации на запрос
(семафор сериализует encode вместо драки потоков за CPU), а шторм из 20
получает быстрые 503 вместо расползания памяти.

Проверки защиты (через прокси):

- `/api/match`: 12 быстрых POST → ровно 10×200, затем 429 (`ok_before_429: 10`).
- Страницы: 125 GET обычным UA → 35×429 после исчерпания 120/мин; следом
  **10 GET с UA Googlebot — все 200** (боты лимитом не режутся).
- Кэш /match: повтор запроса → `took_ms: 0.0`, hit виден в `/health`
  (`cache_hits`, `cache_hit_rate`).

Пример лог-строки `/match` (stdout контейнера, ротация json-file 20 МБ × 5;
формат согласован с eval — процедура отбора кандидатов в
`packages/sfr-match/eval/README.md`):

```json
{"ts": "2026-09-05T13:31:55.257+00:00", "ip_hash": "4e73a25351065e2b",
 "query": "лимитер проверка 10", "query_len": 19, "top1_score": 0.2408,
 "confidence": "none", "below_threshold": true, "cache_hit": false,
 "took_ms": 187.5, "wall_ms": 188.0, "model": "ai-forever/FRIDA",
 "index_version": "frida_clean-535p-abe35971"}
```

## Что не дотянуто (честно)

1. **Выкладки на VPS нет** — не по недоделке, а по пустому блоку параметров
   в спеке (VPS не куплен). Следствия: TLS-выпуск Caddy, DNS, Search
   Console, перемер §3 на бою — не проверены в реальных условиях; репетиция
   покрыла всё, что можно проверить без сервера.
2. **429 на фронте** показывается общим «Сервис недоступен» с «Повторить»,
   без отдельного текста «слишком много запросов». Для пилота приемлемо,
   заметка в NEXT.md.
3. **Кэш /match и счётчики hit-rate живут в памяти процесса** — рестарт
   контейнера их обнуляет; для пилота достаточно, метрики поверх логов.
4. **`make eval`**: воспроизведение подтверждено по диффу
   `docs/SFR2_REPORT.md` (см. чеклист); замечание — прогон шёл параллельно
   с работой контейнеров, латентности в отчёте SFR-2 не сравнивались (они
   и не сравнимы, см. ловушки в `../CLAUDE.md`).
5. **Соль хеша IP** в `make deploy-local` не задана (локально допустимо);
   на бою — обязательный шаг env (`deploy/env.example`).
