## 2. Лейблы

У каждого issue — **ровно один** лейбл «кто» и **один-два** «область».

**Кто делает:**

| Лейбл | Смысл |
|---|---|
| `agent` | делает ночной агент Claude Code по спеке итерации |
| `human` | нужны руки или решение Бориса (купить, проверить глазами, договориться) |
| `sveta` | задача Светы |
| `decision` | открытое решение — сначала решить, потом появятся задачи |

**Область:** `code` (поиск, API, фронт, деплой, данные) · `docs` (паспорт, дек, бриф, Диск,
спека MVP) · `product` (продуктовые решения, пилот, тестеры, юзер-тесты) · `grant` (гранты,
конкурсы, дедлайны) · `design` (дизайн-система, тексты сайта, восприятие) · `legal` (152-ФЗ,
документы сайта, обезличивание).

**Служебные:** `blocked` — ждёт внешнего события или другой задачи; `from-review` — находка
ревью итерации (заменяет §0 следующей спеки).

## 5. Правила для ночного агента

*(этот блок копируется в спеки итераций и кратко продублирован в `CLAUDE.md`)*

- **Перед началом работы:** `gh issue list --label agent --milestone "<текущий>" --state open`
  — это и есть список работ итерации. **Спека уточняет «как», issues — «что».**
- **Коммит, закрывающий задачу, содержит `Closes #N` в теле.** Не закрывать issue вручную
  без коммита.
- **Новая находка по ходу работы** → `gh issue create` с лейблом `agent` + область. Если
  можно сделать в этой же сессии по спеке — сделать и закрыть; иначе оставить открытым.
  Требует человека → лейбл `human`. **Не создавать issue на то, что уже есть** — сначала
  `gh issue list --search`.
- **Находки ревью** (`/review-iteration`) → issues с лейблом `from-review` вместо §0
  следующей спеки.
- **Связи проставлять сразу** — см. §6. Создал issue, у которого есть зависимость или дубль, — комментарий с номером в оба. При массовом создании связи идут вторым проходом в той же сессии.
- **Агент не меняет** milestones, лейблы `sveta` и `decision`, приоритеты и не удаляет issues.
- **`TODO_BORIS.md` и `docs/NEXT.md` удалены 13.09.** «Требует человека» = issue с лейблом `human`; «что уже решено» — сводка в начале `docs/DECISIONS.md`.
- Остальные правила репозитория — в `CLAUDE.md`, они не отменяются.

## 6. Связи между issues — проставлять сразу

Задачи в проекте редко одиночные: одна ждёт другую, одна закрывается вместе с другой, две
описывают одну и ту же работу с разных сторон. **Связь, не записанная номером, не существует:**
в теле issue она выглядит как фраза «пересекается с задачей Светы», и через месяц никто не
поймёт, с какой именно.

**Правило.** Создал issue — сразу проверь, есть ли у него связанные, и оставь комментарий
**в обоих** с номером и словом, объясняющим характер связи:

| Формулировка | Когда |
|---|---|
| «Ждёт #N» | без результата #N начать нельзя — ставить Status `Waiting` и лейбл `blocked` |
| «Блокирует #N» | обратная сторона того же — пишется в блокирующем issue |
| «Та же работа, что в #N» | один заход, разные владельцы или разное оформление результата |
| «Вбирает #N» | мелкая задача делается внутри крупной, отдельно не нужна |
| «Дублируется в #N» | один и тот же пункт пришёл из двух документов — делать в одном заходе |

GitHub сам добавит обратную ссылку в таймлайн второго issue, поэтому достаточно написать номер
через `#`. Ставить связь **в оба** issue всё равно нужно: обратная ссылка в таймлайне видна,
но не объясняет, чем связаны задачи.

**При массовом создании** (миграция, перенос находок ревью, разбор спеки на задачи) номера
появляются только после создания — поэтому связи проставляются **вторым проходом, в той же
сессии**. Это часть работы, а не «потом»: несвязанные issues расходятся уже на второй неделе.

Под-задачи (Sub-issues) использовать только для настоящей иерархии «часть — целое».
Для «блокирует» и «та же работа» отдельного типа связи у GitHub нет — поэтому комментарий.

## 7. Правила для Бориса и Светы

- **Доска** — главный экран: https://github.com/users/borisboriov/projects/5
  Фильтры: [мои руки](https://github.com/borisboriov/search-for-research/issues?q=is%3Aissue+is%3Aopen+label%3Ahuman) ·
  [Света](https://github.com/borisboriov/search-for-research/issues?q=is%3Aissue+is%3Aopen+label%3Asveta) ·
  [решения](https://github.com/borisboriov/search-for-research/issues?q=is%3Aissue+is%3Aopen+label%3Adecision)
- **Вместо пересылки файлов — комментарий в issue.** Замечания, ответы, результаты тестов
  пишутся туда же, где стоит задача: контекст не теряется и его видит агент.
- **Закрыть задачу** = поставить Status `Done` (issue закроется) или нажать Close на самом issue.
- **Новая задача** — кнопка **New issue**: заголовок с глагола, лейблы «кто» + «область»,
  остальное подтянется. Milestone можно не ставить — тогда это бэклог.
- **Status `Waiting`** — задача ждёт человека или внешнего события (объявления гранта,
  результатов пилота). Это не «забыто», это «не наша очередь».

## 8. Шпаргалка `gh`

```bash
gh issue list --label human --state open          # что на мне
gh issue list --label agent --milestone "Пилот 5 тестеров" --state open
gh issue list --search "дедуп"                    # проверить, нет ли уже такого
gh issue create --title "…" --label "agent,code"  # новая задача
gh issue view 42                                  # прочитать
gh issue comment 42 --body "Ждёт #17"             # ответить или связать с другой задачей
gh issue close 42                                 # закрыть руками (агент — через Closes #42)
```
