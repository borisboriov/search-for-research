# NEXT — план SFR-5 (каталог до 12 вузов, дедупликация, перекалибровка)

Вход: MVP-цикл работает end-to-end и отрепетирован в боевой компоновке
(SFR-4: фиксы ревью, серая зона порога, словесные грейды, compose с прокси,
rate limiting, логи, кэш — `docs/SFR4_REPORT.md`). Выкладка на VPS ждёт
только покупки сервера (за Борисом; процедура — `deploy/README.md`).
**Полное ТЗ SFR-5 уже написано: `SPEC_SFR5.md` — источник требований
итерации; этот файл — только навигация и контекст.**

## Что уже решено (не переоткрывать)

- **Модель — `ai-forever/FRIDA`**, запасная — mpnet. Пороги принадлежат паре
  модель×индекс: для `frida_clean` сейчас none=0.27, weak=0.36, high=0.42
  (SFR-4 §0.9); у mpnet своя шкала (0.43). Новый индекс SFR-5 = новая
  калибровка всех порогов, значения — в settings API, не в коде.
- **Бейдж — словесные грейды** (высокое/среднее/слабое), процент в tooltip;
  границы грейдов отдаёт API (`/health`), фронт чисел не знает. Решение
  Бориса 05.09 — не откатывать на проценты.
- **Серая зона — баннер, не отказ**: confidence weak показывает выдачу
  с предупреждением. Академически звучащие OOD-запросы (backend, филология)
  пробивают старый порог — для них и сделана зона; SFR-5 добавляет ≥10 таких
  в OOD-набор.
- **Карточки открытые и бесплатные**, SEO — органический канал: rate
  limiting ботов не режет (проверено с UA Googlebot), sitemap = весь каталог.
- **Компоновка** — deploy/docker-compose.yml (api без внешних портов + web +
  Caddy с rate limiting и авто-TLS). Артефакты доставляются
  (`deploy/sync-artifacts.sh`), на сервере не собираются. Новый индекс SFR-5
  должен попадать в этот скрипт (сейчас он возит `data/indexes_sfr2` —
  обнови пути).
- **Пересозданный контейнер web теряет ISR-кэш** → пост-деплойная
  ревалидация (`POST /api/revalidate` с секретом) — обязательный шаг
  каждого деплоя, уже в README и make deploy-local.
- **Логи /match** — источник кандидатов для перекалибровки: формат и
  процедура отбора — `packages/sfr-match/eval/README.md`.
- **PostgreSQL/pgvector — не сейчас**: на 5–8 тыс. профилей файловый индекс
  ещё достаточен; переезд — когда корпус перерастёт десятки тысяч.
- **eLibrary и скрейпинг сайтов вузов — вне скоупа** (юр. решение проекта);
  эксперимент с контактами в SFR-5 — только измерение, в продукт не встраивать.

## Ядро SFR-5 (детали — в SPEC_SFR5.md)

1. **Каталог**: +10 вузов (ВШЭ, СПбГУ, ИТМО, Бауманка, МИФИ, МИСИС,
   Иннополис, МАИ, НГУ, УрФУ), отбор со стратификацией по областям — чтобы
   CS/экономика/гуманитарные не вытеснялись физикой мегаколлабораций.
   Целевой корпус 5 000–8 000 профилей.
2. **Дедупликация** (долг SFR-0): склейка расщеплённых профилей по
   ORCID/пересечению работ; детектор чужих склеек OpenAlex — флаг, не
   расклейка. Проверить, что превью-профили лендинга пережили дедупликацию.
3. **Качество**: регрессия Success@1/@5 на новом корпусе (просядет —
   ожидаемо, фиксировать честно), перепроверка OOD-набора, перекалибровка
   обоих порогов, прогон внешних запросов (включая e01 про backend).
4. **Эксперимент с контактами**: % email через ORCID/Crossref/ручную
   проверку на 50 профилях — измерение для решения Бориса.

## Хвосты SFR-4, тянущиеся в SFR-5

- **Выкладка на VPS** — как только будет сервер: `deploy/README.md`,
  перемер §3 SPEC_SFR4 на бою (локальные цифры — `docs/sfr4_bench.json`),
  Search Console / Яндекс.Вебмастер.
- **Внешний тест-сет**: в `external_queries.jsonl` пока один запрос (e01,
  от Бориса). 10–15 запросов студентов собирают Борис и Света; пилот с 5
  тестерами (`docs/PILOT_TEST_GUIDE.md`) даст ещё ~5.
- **429 на фронте** показывается как «Сервис недоступен» с «Повторить» —
  без отдельного текста «слишком много запросов». Для пилота терпимо.
- Судейство SFR-2: проверена выборка 20 из 171; остальное — по мере
  надобности.
