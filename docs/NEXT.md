# NEXT — план SFR-2 (API поиска)

Вход: `data/exports/profiles.jsonl` (261 профиль, SFR-0) + выбранная в SFR-1 модель
и порог отсечки. Итоги мини-теста — `docs/SFR1_REPORT.md`.

## Что уже решено в SFR-1 (не переоткрывать)

- **Модель: `ai-forever/FRIDA`** (823M, dim 1536, префиксы `search_query:` /
  `search_document:`). Success@5 = 100% при пороге проекта 70%, и он устоял при
  удвоении корпуса (МФТИ+МГУ, 535 профилей). Запасной вариант при требованиях
  к латентности — `paraphrase-multilingual-mpnet-base-v2` (95%, 20 мс вместо 136 мс).
- **Метрику качества дополнить Success@1.** Проверка на втором вузе показала, что
  Success@5 при k=5 слишком груб: он не заметил удвоения корпуса вообще, тогда как
  Success@1 просел с 86% до 77%. Студент смотрит на верхнюю строчку — значит и
  порог продукта должен её измерять.
- **Порог «никого не нашли»: 0.35 по top-1 score**, и не как отказ, а как
  предупреждение — при перекрытии распределений жёсткий отказ режет живые запросы.
- **Чистка profile_text включена**, хотя измеримого эффекта на поиск не дала:
  бесплатна и нужна, когда профили начнут показывать пользователю.
- **BM25-гибрид не делаем**: у 16 из 30 запросов нулевой лексический score
  (русский запрос против англоязычного профиля). Нужен перевод запроса — отдельная задача.

## 1. FastAPI `/match` (`apps/api/`)

- `POST /match {query: str, k: int = 10}` → `{results: [{author_id, name, institution,
  h_index, topics, score, profile_text}], below_threshold: bool}`.
  `below_threshold = top1_score < 0.35` — фронт показывает «уверенных совпадений нет».
- Модель и индекс грузятся один раз при старте (`lifespan`), не на запрос: загрузка
  FRIDA — единицы секунд, поиск — 136 мс. Прогрев (`Backend.warmup()`) на старте обязателен.
- Переиспользовать `sfr_match.search.load_backend` — не дублировать логику в API.
- Индекс собирается офлайн (`make index`) и монтируется в контейнер; API его не строит.
- Health-эндпоинт с версией индекса (`meta.json`) — чтобы видеть, что API и индекс не разъехались.

## 2. Вернуть FAISS на путь поиска

На macOS faiss и torch конфликтуют по libomp, поэтому поиск сейчас — точный NumPy-скан
(см. DECISIONS.md). В Linux-контейнере конфликта нет: включить FAISS обратно и
проверить тестом `test_numpy_scan_matches_faiss_exactly`, что выдача не изменилась.
На 261 профиле разницы в скорости не будет — это задел под рост корпуса.

## 3. Данные и оценка (долги SFR-1)

- **Перепроверить судейство человеком**: `packages/sfr-match/eval/judgments_for_review.md`
  (20 случайных пар). Все 616 оценок поставила LLM — до проверки метрики предварительные.
- **Расширить out-of-domain**: нужно ≥15 честных посторонних запросов. Сейчас их два
  (q28 право, q30 маркетинг): q27 и q29 неожиданно нашли реальные ответы в корпусе.
  Без этого порог 0.35 стоит на двух точках.
- ~~**Второй вуз**~~ — сделано 29.08 (МГУ, корпус 535). Следующий шаг здесь —
  не третий вуз, а **рост масштаба**: 535 профилей это всё ещё пилот, и вопрос
  «что будет на 5–50 тысячах» открыт. Заодно там впервые станет осмысленным
  IndexFlatIP против чего-то с приближённым поиском.
- **Состав `profile_text` как отдельный эксперимент**: mpnet видит только первые
  128 токенов (имя + темы + начало первой работы) и берёт 21/22 — значит, основной
  сигнал в строке ключевых тем. Стоит померить варианты: только темы / темы + названия /
  полный текст.
