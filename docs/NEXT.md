# NEXT — план SFR-4 (деплой и подготовка пилота)

Вход: полный MVP-цикл работает локально — ETL (SFR-0) → FRIDA (SFR-1) →
API (SFR-2) → фронт (SFR-3). Итоги фронта — `docs/SFR3_REPORT.md`.
SFR-4 — вывод этого цикла на публичный адрес и подготовка к 5 тест-пользователям.

## Что уже решено (не переоткрывать)

- **Модель — `ai-forever/FRIDA`**, запасная — mpnet (`SFR_API_MODEL` + свой индекс
  и порог 0.43). Порог FRIDA 0.27 — предупреждение, а не отказ.
- **Карточки НР открытые и бесплатные**, без авторизации. SEO — органический
  канал: SSR + sitemap уже реализованы и проверены (Lighthouse SEO 100), rate
  limiting не должен резать поисковых ботов.
- **Индекс собирается офлайн** и монтируется; локальный `make api` и контейнер
  сервят `data/indexes_sfr2`. **Обогащение карточек** — `data/exports/cards.jsonl`
  (`make export-cards`): файл gitignored, на VPS его нужно собрать или привезти
  вместе с индексом — иначе карточки без работ и цитирований (API при этом
  работает, это штатная деградация).
- **Фронт**: Next.js, npm, Node 24; прод-сборка standalone; сборка не требует
  живого API. Прокси `/api/match` — клиент в API напрямую не ходит.
- **Бейдж «NN%» показывает косинусную близость честно** (30–45% на живых
  запросах). Менять шкалу только решением Бориса (TODO_BORIS).
- **PostgreSQL/pgvector, RAG-объяснения, авторизация/ЛК, новые вузы** — вне скоупа.

## 1. Деплой (ядро SFR-4)

- РФ-VPS (8 ГБ RAM, ≥2 vCPU, ≥20 ГБ — измерено в SFR-2; покупка за Борисом),
  домен search-for-research.ru.
- Компоновка: docker compose — API + фронт (standalone) + reverse-proxy
  (nginx/caddy) с TLS; артефакты (индекс, cards.jsonl, веса модели) доставляются
  на сервер, не собираются там.
- `NEXT_PUBLIC_SITE_URL` = боевой домен (канонические URL и sitemap), проверить
  выдачу sitemap на бою и отдать в Search Console / Яндекс.Вебмастер.
- Перемерить на VPS: латентность /match под нагрузкой, TTFB страниц, Lighthouse
  Performance (локальные 94 не переносимы).

## 2. Защита и наблюдаемость API (до публичной ссылки — обязательны)

- **Rate limiting** на /match (каталожные GET — щадяще, ботов поиска не резать).
- **Логи запросов**: текст, top-1 score, `below_threshold`, латентность —
  это и мониторинг, и материал следующей калибровки порога.
- **Кэш ответов** на повторные запросы (дешёвый способ поднять потолок FRIDA
  с её ~2 rps).
- Health-мониторинг + перезапуск контейнеров (restart policy, простой uptime-чек).

## 3. Пилот на 5 тест-пользователях

- Сценарий теста и форма обратной связи — Борис + Света (TODO Светы в проекте).
- До пилота закрыть решения из TODO_BORIS: маппинг score→%, тексты лендинга,
  email-шаблон, три профиля превью, `NEXT_PUBLIC_CLAIM_EMAIL`.
- Собранные запросы пилота — кандидаты во внешний тест-сет (не показывать
  корпус заранее — правило из eval/README).

## 4. Данные и оценка (долги, тянутся)

- **Внешний тест-сет пуст** — самое слабое место линии измерений (собирают
  Борис и Света, инструкция готова).
- **Дедупликация авторов** (долг SFR-0): склейки видны на страницах НР
  (пример — «свежая работа» про Т-клетки у NLP-профиля). До пилота хотя бы
  оценить масштаб; чинить — отдельной итерацией.
- **Источники недостающих полей карточки**: должность, email, журналы изданий —
  контракт API уже несёт поля, нужен источник (claim profile, ручная разметка
  топ-профилей?). Продуктовое решение за Борисом.
- Судейство SFR-2: выборка 20 из 171 проверена; остальное — по мере надобности.

## Вне SFR-4

- PostgreSQL + pgvector — когда корпус перерастёт десятки тысяч профилей.
- RAG-объяснение «почему этот НР»; serendipity-флаг в API (фронт уже умеет
  его рисовать — см. /dev/states).
- ЛК, сохранённые подборки, отправка писем из сервиса, C6/позиции НР, тёмная
  тема (shadcn даёт почти бесплатно — только по итогам пилота).
