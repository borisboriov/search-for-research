## 2026-08-28 — uv workspace с виртуальным корнем

Корневой `pyproject.toml` без build-system (сам по себе не пакет), два
workspace-пакета `sfr-core` и `sfr-etl` с hatchling. Dev-зависимости — в
dependency-group `dev` корня.
**Почему:** корень не содержит кода; hatchling — стабильный минимальный бэкенд.
**Альтернативы:** uv_build (моложе, меньше документации), setuptools (тяжелее).

## 2026-08-28 — конфиги инструментов в корневом pyproject.toml

ruff/mypy/pytest/coverage настроены один раз в корне, а не по-пакетно.
Разная строгость mypy — через per-module override (`sfr_core.*` strict).
**Почему:** один источник настроек, `make lint`/`typecheck`/`test` работают из корня.
**Альтернативы:** по-пакетные конфиги — дублирование и рассинхрон.

## 2026-08-28 — macOS: UF_HIDDEN на .venv ломает editable-импорты → `make unhide`

На macOS uv помечает содержимое `.venv` флагом `UF_HIDDEN`, а CPython (3.13 и
бэкпорт в 3.12.13) пропускает hidden `.pth`-файлы в site-packages — editable-пакеты
workspace молча перестают импортироваться (`ModuleNotFoundError: sfr_core`).
**Решение:** цель `unhide` в Makefile (`chflags -R nohidden .venv`), прогоняется перед
всеми uv-командами; на Linux/CI — no-op. Плюс пин Python 3.12 (`.python-version`) —
версия из SPEC и CI.
**Альтернативы:** не-editable установка (`--no-editable`) — неудобно при разработке;
PYTHONPATH-хаки — маскируют проблему.

## 2026-08-28 — сверка с реальным OpenAlex API (пробные запросы)

Расхождения со SPEC/ожиданиями, зафиксированные по фактическим ответам:

- У Institution **нет поля name_ru**: русское название лежит в
  `display_name_alternatives` (у МФТИ `international.display_name.ru = null`).
  Решение: `name_ru` = первая кириллическая строка из `display_name_alternatives`, nullable.
- У Author `last_known_institutions` — **список** (у одного автора до 3+ институтов),
  а не единственный FK. Решение: в БД храним один FK — целевой институт ингеста
  (тот, по которому автор был найден); полный список остаётся в `raw` JSON.
- Метрики автора лежат в `summary_stats` (`h_index`, `i10_index`, `2yr_mean_citedness`).
- Фильтр авторов по вузу: используем `last_known_institutions.id:<ID>` (у МФТИ 7649
  авторов) — «текущая» аффилиация релевантнее для подбора НР, чем историческая
  `affiliations.institution.id`. Сортировка `works_count:desc`, cursor-пагинация
  (`meta.next_cursor`) — подтверждены.
- Работы: `abstract_inverted_index` (nullable), `topics[].score`, `title == display_name`,
  параметр `select=` работает — используем для сокращения трафика.
- «Свежесть» публикации автора на этапе ингеста авторов определяем по `counts_by_year`
  (годы с `works_count > 0`), т.к. работ в БД ещё нет; порядок элементов не гарантирован —
  фильтруем по значению года. «Последние N лет» = календарные годы `>= current_year - N + 1`.
- Данные: топ по works_count — участники мегаколлабораций (напр. «A. Zhemchugov»,
  2847 работ, h=152, 100+ соавторов на работу) — кандидаты в проблемы качества для REPORT.

## 2026-08-28 — Work: составная уникальность (author_id, openalex_id), а не по openalex_id

Одна и та же работа законно попадает в профили нескольких кандидатов (соавторство
внутри вуза: на прогоне — 351 такая работа).
**Почему:** SFR-0 хранит связку «в чьём профиле учитываем» (§3 SPEC), а не полную
many-to-many авторство; уникальность только по `openalex_id` теряла бы работу у
всех соавторов, кроме первого.
**Альтернативы:** отдельная таблица authorship — избыточно для SFR-0.

## 2026-08-28 — отбор работ: половина бюджета цитируемым, половина свежим

`merge_work_records`: `ceil(per_author/2)` самых цитируемых + свежие до лимита,
дедупликация по id, добор цитируемыми, если свежих мало.
**Почему:** профиль должен отражать и вес учёного (цитируемость), и то, чем он
занят сейчас (для подбора НР это важнее). Два запроса на автора вместо одного —
приемлемая цена (523 запроса на 261 автора).
**Альтернативы:** только цитируемые (профиль «замораживается» на старых хитах),
только свежие (теряется вес).

## 2026-08-28 — «свежесть» автора считается по counts_by_year, а не по работам

На шаге `etl authors` работ в БД ещё нет, поэтому `is_supervisor_candidate`
использует `counts_by_year` из ответа API (годы с `works_count > 0`).
**Почему:** иначе шаги пришлось бы связать в один проход и потерять
идемпотентность/кэшируемость по отдельности.
**Альтернативы:** пересчёт флага после ингеста работ — можно добавить в SFR-1,
если пороги начнут крутиться.

**Почему:** `x_concepts` помечены OpenAlex как deprecated; `topics[].count` —

**Альтернативы:** `topic_share` (доля) — менее интерпретируемо в отчёте.

**Альтернативы:** править REPORT.md руками после каждой генерации — рассинхрон.

## 2026-08-29 (SFR-1) — отдельный пакет `sfr-match`, а не расширение `sfr-etl`

Третий workspace-пакет `packages/sfr-match` (`src/sfr_match/`), зависит от `sfr-core`.

## 2026-08-29 — русско-специализированная модель: `ai-forever/FRIDA`

§3.3 SPEC_SFR1 требует модель из топа ruMTEB (retrieval) < 1.5B. Взята FRIDA
(823M параметров, FRED-T5-энкодер, префиксы `search_query: ` / `search_document: `).
**Почему:** топовая по ruMTEB модель, укладывающаяся в лимит: лидер лидерборда
GigaEmbeddings — 7B+, вне лимита. Доступность проверена через HF API
(`gated: false`), модель грузится в sentence-transformers 6.0 и отдаёт dim=1536.
**Альтернативы:** `ai-forever/ru-en-RoSBERTa` (404M, билингвальная — запасной вариант,
если бы FRIDA не загрузилась), `deepvk/USER-bge-m3` (359M), `sergeyzh/BERTA` (128M).
**Риск, зафиксированный заранее:** карточка FRIDA прямо пишет, что модель заточена
под русский, а качество на английском неизвестно — а корпус профилей в основном
англоязычный. Это и меряем.

## 2026-08-29 — FAISS пишет индекс, поиск считает NumPy (конфликт libomp на macOS)

`faiss-cpu` и `torch` линкуют по своей копии libomp; на macOS второй инициализатор
роняет процесс (`OMP: Error #15`) ровно на `IndexFlatIP.search`. Порядок импорта не
спасает, `omp_set_num_threads(1)` тоже; единственный переключатель
`KMP_DUPLICATE_LIB_OK=TRUE` сам upstream описывает как способный «silently produce
incorrect results».
**Решение:** FAISS пишет `index.faiss` (артефакт для SFR-2), рядом кладётся
`vectors.npy`; поиск — точный NumPy-скан по внутреннему произведению. На 261 профиле
это точно и занимает доли миллисекунды. Равенство двух путей проверяется тестом
`test_numpy_scan_matches_faiss_exactly`. Сборка индекса (torch + faiss в одном
процессе) безопасна при порядке «сначала эмбеддер, потом faiss» — так и сделано.
**Почему не «выкинуть FAISS»:** §2 SPEC_SFR1 требует FAISS-индекс, и в проде (Linux)
конфликта нет — формат хранения должен быть тот, с которым поедет SFR-2.
**Альтернативы:** `KMP_DUPLICATE_LIB_OK=TRUE` (риск молча неверных чисел в
эксперименте, чей единственный результат — числа); считать эмбеддинги и поиск в
разных процессах (усложняет CLI ради машины разработчика).

## 2026-08-29 — clean-варианты построены для всех моделей, а не только для лучшей

§5 SPEC_SFR1 просит прогнать в clean/no-clean лучшую модель. Построены оба варианта
для всех пяти.
**Почему:** судейский пул собирается один раз по объединению топ-5 всех прогонов;
если clean-вариант добавить после разметки, придётся доразмечать вторым раундом —
и часть пар будет оценена в другом контексте. Дешевле проиндексировать вдвое больше
(261 профиль), чем получить неоднородную разметку.

## 2026-08-29 — `paraphrase-multilingual-mpnet-base-v2` оставлен с `max_seq_length=128`

Модель обрезает вход на 128 токенах — это меньше, чем profile_text (до 1500 символов).
Лимит не поднимался.
**Почему:** 128 — то, на чём модель обучалась и как она поставляется; поднять окно
значит мерить не ту модель, которую кто-то возьмёт «из коробки». Ограничение
зафиксировано в отчёте как объяснение результата, а не спрятано.

## 2026-08-29 — судейство: пул топ-5, сортировка по author_id, неоценённые = grade 0

Пул — объединение топ-5 всех 10 вариантов; пары сортируются по `(query_id, author_id)`,
а не по score, чтобы судья не видел, какая модель их выдала. Пары в топ-10, не попавшие
в пул, считаются нерелевантными при расчёте nDCG@10.
**Почему:** стандартная практика pooled evaluation (TREC): полная разметка 30×261
невозможна, а «неоценённое = 0» одинаково штрафует все модели. Доля оценённых пар
в топ-5 выводится в отчёт отдельной таблицей — чтобы видно было, где оценка неполна.

## 2026-08-29 — CLI: сверх четырёх команд §2 добавлены `pool`, `review-sample`, `stats`

`pool` выгружает пул пар для судейства, `review-sample` пишет `judgments_for_review.md`,
`stats` показывает, что меняет чистка на текущем корпусе.
**Почему:** §5 требует и пул, и файл на ручную проверку; делать их разовыми скриптами
значит потерять воспроизводимость `make eval`.

## 2026-08-29 — рубрика судейства: grade 2 = «покрыто главное содержание запроса»

На составных запросах (например q07 «deep learning для физики частиц») буквальное
«прямое совпадение специализации» не встречается ни у кого. Принято правило: grade 2
ставится, если профиль покрывает то, ради чего студент ищет НР, а не любую половину
формулировки. Для q07 это данные с детекторов (метод студент приносит сам), поэтому
экспериментаторы ATLAS/CMS получили 2, а «чистые» ML-специалисты — 1.
**Почему:** иначе либо ни один запрос не имеет grade=2 (метрика вырождается), либо
grade=2 получает всё подряд (метрика перестаёт различать модели).
**Альтернатива:** отдельные оценки по каждой половине запроса — усложняет разметку
вчетверо ради запросов, которых 1–2 на набор.

## 2026-08-29 — чистку profile_text оставляем включённой, несмотря на нулевой эффект

Clean меняет 46 из 261 профилей (медиана 30 символов) и сдвигает Success@5 на ±1

## 2026-08-29 (SFR-2) — карточки НР отдаются без авторизации

`/api/match` и `/api/supervisors/{id}` возвращают полную карточку (имя, вуз, h-index,

**Почему:** это не техническое упрощение, а продуктовое решение из плана MVP v1.3 —
карточки открытые и бесплатные, монетизация строится на сервисах вокруг данных
(сопровождение, аналитика для вузов), а не на самих данных. Прятать за авторизацией
то, что уже открыто в OpenAlex, значит создавать трение без выручки.
**Следствие:** авторизация не появляется и в SFR-3; если продуктовое решение
изменится, менять придётся и контракт API, и фронт.

## 2026-08-29 (SFR-2) — бэкенд поиска выбирается по платформе

`select_search_backend()`: FAISS везде, кроме macOS, где faiss и torch конфликтуют
по libomp (разбор — в `runtime.py` и в решении от 29.08 про NumPy-скан). Переключатель
`SFR_SEARCH_BACKEND=faiss|numpy` перекрывает автоматику.
**Почему не «FAISS везде»:** конфликт на macOS не лечится, а разработка идёт на macOS.
**Почему не «NumPy везде»:** на 535 профилях разницы нет, но файловый IndexFlatIP —
это задел под рост корпуса, и проверять его надо там, где он будет работать.
**Оговорка, которую нашёл тест:** на точных ничьих порядок расходится — NumPy
разрешает их по индексу (stable sort), FAISS нет. Поэтому эквивалентность
проверяется как «те же документы + те же score», а порядок — только там, где
score различаются. На живых 1536-мерных векторах ничьих не бывает, но на
вырожденных данных (и в юнит-тестах с фейковым эмбеддером) бывают.

## 2026-08-29 (SFR-2) — torch на Linux ставится с CPU-индекса PyTorch

В корневом `pyproject.toml` объявлен `[[tool.uv.index]] pytorch-cpu` и источник
`torch = [{ index = "pytorch-cpu", marker = "sys_platform == 'linux'" }]`; сам

**Почему:** первый собранный образ весил **10.3 ГБ** — в нём лежали CUDA-колёса
(`nvidia-*`, `triton`), которых на CPU-VPS не будет никогда. После правки — **2.4 ГБ**.
Это прямо влияет на выбор хостинга: 10 ГБ образа требуют другого тарифа по диску.
**Почему через marker, а не глобально:** на macOS у CPU-индекса нет колёс, разработка
там бы сломалась.

## 2026-08-29 (SFR-2) — порог отсечки принадлежит варианту индекса, а не проекту

Калибровка считается по `frida_clean` (полный profile_text) — тому варианту, который
реально обслуживает API.
**Почему:** score — это косинус между запросом и текстом профиля; если в индексе
лежат только темы, распределение score другое, и порог, снятый с полного текста,
на нём ничего не значит. Эксперимент §5 отвечает на вопрос «что класть в индекс
дальше», а не «что стоит в проде сейчас», поэтому порог калибруется на текущем прод-варианте.
**Следствие:** если по итогам эксперимента состав индекса поменяется — порог придётся
калибровать заново, и это надо будет написать в отчёте, а не унаследовать число.

## 2026-08-29 (SFR-2) — модель не запекается в образ, «холодный старт» считается без скачивания

Dockerfile не содержит весов; HF-кэш монтируется томом (`HF_HOME=/models`), при замере
ресурсов — bind-mount хостового кэша.
**Почему:** FRIDA — это ~2 ГБ поверх образа, они не меняются между релизами кода,
и запекать их значит гонять их при каждом деплое. Плюс переключение модели
(`SFR_API_MODEL=mpnet`) не должно требовать пересборки образа.
**Как это влияет на цифру:** «холодный старт» в отчёте — это загрузка модели с диска
в память, без сетевого скачивания. Первый в жизни запуск на пустом томе будет дольше
на время скачивания; это оговорено в отчёте.

умолчанию, поэтому индексы SFR-1 продолжают читаться.

## 2026-09-05 (SFR-4b) — бинарные сканеры: PATH → docker, в CI — релизные бинарники

## 2026-09-05 (SFR-5) — отбор авторов: квота с раскладкой по областям вместо works_count:desc

`sfr etl authors --strategy stratified --quota N`: пул = все авторы вуза,
проходящие пороги эвристики НР (серверный фильтр OpenAlex + локальная проверка

## 2026-09-05 (фиксы ревью SFR-5) — агрегаты склейки пересобираются из `raw`

## 2026-09-06 (бэкфилл) — сеть и запись в БД разделены

`scripts/warm_works_cache.py` в несколько потоков выкачивает те же два запроса
на автора, что делает ингест, и складывает их в дисковый кэш; затем

означает «дневные кредиты кончились до полуночи UTC». Ретраи только жгут время,
а прогресс и так на диске — повторный запуск продолжит с того же места.
**Цена:** два шага вместо одного и знание, что их надо запускать по порядку;
записано в README, CLAUDE.md и NEXT.

## 2026-09-06 (ревью SFR-5) — порог `none` 0.37 → 0.32: четыре запроса с устаревшей меткой

Четыре запроса golden set (`q27` история России, `q28` гражданское право,
`q29` выпечка хлеба, `q30` маркетинг в соцсетях) с SFR-1 несли метку
`out-of-domain`. В калибровку они не входили никогда: `_calibration` берёт из
golden set только `in-domain` и `edge`, а посторонние — из `ood_queries.jsonl`.
На корпусе 12 вузов метки устарели ровно так же, как у `o07`, но заметить это
было негде, и отчёт SFR-5 сделал из их отсутствия вывод «распределения
разошлись начисто, зазор 0.363…0.391».

**Проверено процедурой из `eval/ood_verification.md`** (прямой прогон +
контрольный перефраз): посторонним не остался ни один. `q29` и `q30` — прямые
попадания (пищевые технологи ИТМО, маркетологи ВШЭ/СПбГУ), помечены
`in-domain`; `q27` и `q28` — специалист есть, но тема на периферии корпуса,
помечены `edge`.

**Следствие:** зазора нет, распределения перекрываются — посторонний максимум
0.363 (`o34`, киноведение, в §6 отчёта помечен спорным) против настоящего
минимума 0.349 (`q27`). Порогов выше 0.348, не режущих настоящие запросы, не
существует. Плато максимального покрытия среди безопасных — [0.283…0.348],
его середина **0.32**: 18 из 19 посторонних, ноль ошибочных отсечек.

**Почему не оставить 0.37.** Он показывал бы «уверенных совпадений нет» на
запросе, где нужный человек стоит первым с оценкой 2. Цена снижения — один
посторонний (0.363) больше не отсекается, но попадает в серую зону [0.32, 0.40)
и получает баннер «совпадения слабые». То есть спорный запрос получает
предупреждение вместо отказа, а не выдаётся как уверенный ответ.

**Почему выбор меток не подгонка:** рекомендация калибровки равна 0.32 при любом
варианте разметки этих четырёх (обе `edge`, обе `in-domain`, все четыре в одну
сторону) — метки на порог не влияют.

**Побочно закрыто:** отчёт и `sfr_match.calibrate.recommend` теперь дают одно и
то же число; в первой редакции отчёт брал 0.37, а код рекомендовал 0.38.
`weak` = 0.40 и `high` = 0.47 не изменились (медиана top-1 сместилась
0.4768 → 0.4791, на сетке 0.01 вниз это то же значение).

**Альтернативы:** оставить метки как есть и не трогать порог — отвергнуто,
метка опровергнута данными; выкинуть `q27`–`q30` из набора — отвергнуто,
это четыре нормальных студенческих запроса, и корпус на них отвечает.

## 2026-09-06 (ревью SFR-5) — штамп порогов шагом сборки индекса

`make index-sfr5` писал свежий `meta.json` без порогов, а штамп ставился руками

## 2026-09-06 (ревью SFR-5) — общий колпак rps на прогреве кэша

`scripts/warm_works_cache.py` троттлил внутри потока: суммарный темп был
`workers × rps-per-worker`, и `settings.openalex_max_rps` не использовался вовсе.
Дефолт 6×1.2 = 7.2 rps укладывался в правило «≤10 rps» случайно, а `--workers 10`
молча его нарушал. Докстринг при этом обосновывал схему несуществующим «жёстким
лимитом OpenAlex в 100 запросов в секунду».

**Решение:** `RateLimiter` в `sfr_etl.client` — общий на все потоки, резервирует
слот под блокировкой и спит вне её (иначе потоки выстраивались бы в очередь на
время сна). Клиент принимает его опционально; `max_rps` остаётся верхней
границей для потока. Скрипт печатает запрошенный темп и колпак, и предупреждает,
когда первый выше второго.


## 2026-09-08 (выкладка) — `www` обслуживается как второй адрес Caddy, а не редиректом

DNS делегирован и на апекс, и на `www`, поэтому имя `www.search-for-research.ru`

ветки конфигурации ради редиректа в момент первой выкладки — риск ради
косметики; сделать отдельно, когда будет повод трогать Caddyfile.

**Побочно:** значение с запятой и пробелом обязано быть в кавычках — `source .env`

## 2026-09-11 (дизайн, референс-банк) — процент совпадения убран со страницы профиля

На `/supervisor/:id` справа стоит крупный бейдж «43% — совпадение с твоим
запросом», хотя в списке результатов у того же НР — словесный грейд «среднее
совпадение». Это расхождение с уже принятым решением («бейдж — словесные грейды,
процент в tooltip», см. `docs/NEXT.md`, «Что уже решено»): на профиле процент
вынесен в главный визуальный акцент. Замечено при съёмке baseline живого сайта
11.09 — `../02_research/2026-09_дизайн_референсы/baseline_live_2026-09-11/`,
наблюдение 1. Числом 43% пользователь пользоваться не может: он не знает ни шкалы,
ни порогов, и читает его как школьную оценку — «плохо».

**Решение:** процент со страницы профиля убрать. Остаётся словесный грейд, как в
списке, плюс строка, называющая, **чем** совпадение подкреплено: «совпало N тем
из M в запросе». Косинус остаётся в tooltip и в ответе API — там он для нас, а не
для студента.

**Метод выбора — сравнение с живыми продуктами, а не вкус** (референс-банк фазы 1,
`../02_research/2026-09_дизайн_референсы/Дизайн_референсы_2026-09.md`):

- **Consensus** (карточка P-18) показывает уверенность как долю свидетельств:
  полоса «19 за / 1 против» с подписью «N = 20» и подрисуночной подписью, как у
  рисунка в статье. Не одно число, а из чего оно получилось.
- **Профи.ру** (P-28) рядом с «98% положительных отзывов» мелким шрифтом печатает
  знаменатель — из скольких отзывов и за какой период.
- **Google Scholar** (P-13) даёт метрики в двух колонках, «всего» и «за пять
  лет»: сравнение делает число осмысленным.

**Альтернативы:** (а) вернуть процент и в список — отвергнуто вместе с решением о
словесных грейдах; (б) оставить процент везде, убрав грейд — отвергнуто: порог
принадлежит паре модель×индекс, и после пересборки индекса тот же НР получит
другой процент без изменения смысла; (в) не трогать — отвергнуто: расхождение
видно на одном и том же НР за один клик.

**Зависимость:** строка «N тем из M» требует полей в ответе `/match`, которых
сейчас нет, — это задача ранжирования SFR-6. До неё на профиле остаётся словесный
грейд без строки-подкрепления; это всё равно лучше, чем «43%».

## 2026-09-12 (SFR-6) — грейд на профиле приходит ссылкой, а не считается фронтом

Решение 11.09 убрало с `/supervisor/:id` бейдж «43%» и оставило словесный
грейд. Но грейд — это функция порогов (`score_weak`, `score_high`), а пороги
принадлежат паре модель×индекс и живут в настройках API. У фронта два способа
его получить: (а) вытащить пороги из `/health` и сравнить с `?score=`
самостоятельно; (б) принять готовый грейд от API.

**Решение:** (б). Карточка выдачи кладёт в ссылку на профиль `&grade=`
(`high` / `medium` / `low` / `serendipity`) рядом с уже передаваемым `?score=`;
островок `MatchGrade` только валидирует значение и рисует тот же `MatchBadge`,
что в списке. Пришли на профиль напрямую — блока нет, как и раньше.

**Почему не (а):** правило «фронт ничего не считает сам» появилось ровно из-за
порогов — после пересборки индекса тот же НР получает другой косинус без
изменения смысла. Вариант (а) дублирует на фронте логику, которая уже есть на
бэкенде, и делает страницу зависимой от ещё одного запроса к `/health` только
ради classification.

**Цена:** ссылка стала длиннее, а грейд в ней — подделываемым. Это терпимо:
страница открыта и анонимна, подделать можно и `?score=`, а вреда от чужого
слова «высокое совпадение» на своей же вкладке нет.

**Попутно:** косинус остался в tooltip бейджа. Требование спеки «процент нигде»
читается как «процент не бывает видимым элементом»: решение 11.09, на которое
спека ссылается, явным текстом оставляет косинус в tooltip — там он для нас, а
не для студента.

## 2026-09-12 — поисковые кабинеты: Domain-property и DNS вместо файла/метатега

Пункт `TODO_BORIS.md` «Search Console» закрыт вместе с Борисом, и по ходу
выяснилось, что он покрывал только половину задачи.

**Тип ресурса — Domain, не URL prefix.** Domain-property покрывает апекс, `www`
и оба протокола одним ресурсом. Это важно именно у нас: `www` и апекс оба
отдают сайт (решение 08.09 не делать 301), и URL-prefix-ресурс собирал бы
статистику только по одному из имён.

**Подтверждение — DNS TXT, не HTML-файл и не метатег.** Оба альтернативных
способа означают правку `apps/web` → пересборку образа web → выкладку на VPS
ради одной строки. DNS-запись ставится за две минуты и не трогает боевой стенд.
Побочный плюс: она не может «потеряться» при следующей пересборке фронта.

**Подключён и Яндекс.** Целевая аудитория — российские студенты, а в России
основной поиск Яндекс; кабинет только в Google закрывал бы меньшую часть
аудитории. Вебмастер подтверждён такой же TXT-записью в той же группе записей
зоны (`yandex-verification: …` рядом с `google-site-verification=…`), sitemap
отправлен и там.

**Следствие для эксплуатации:** в зоне `search-for-research.ru` TXT-группа
апекса теперь несёт два токена верификации. Удаление любого из них отключает
соответствующий кабинет — записано в `TODO_BORIS.md`.

**Проверено по ходу:** обход 5 538 страниц не упрётся в лимитер — зона `pages`
в `deploy/proxy/Caddyfile` исключает поисковых ботов по User-Agent (заложено
в SFR-4); sitemap отдаётся под UA Googlebot за 76 мс, 200, `application/xml`.

## 2026-09-26 (SFR-5c) — потолок на вуз: правило, а не только числа (МГУ 1 800, СПбГУ 1 200)

Каталог шага 1 дорожки данных (#98) собран стратифицированным отбором с
**потолком для двух крупнейших пулов**: МГУ — 1 800, СПбГУ — 1 200, остальные
десять вузов без квоты (`--quota 100000`, при квоте ≥ пула `allocate_quota`
отдаёт области целиком). Пол на область — по умолчанию (8), `catalog.py` не
менялся.

**Правило, по которому получены числа** (чтобы #99 применял его, а не заводил
спор заново, — пожелание ревью спеки):

> Потолок ставится только вузам, чей пул годных больше самого большого пула
> **без** потолка. Базовая величина = этот наибольший пул без потолка
> (здесь ВШЭ, 1 175 → 1 200 с округлением до сотен). Второй по размеру вуз
> получает ×1,0 от базы, крупнейший — ×1,5.

Отсюда 1 200 и 1 800: ни один вуз с потолком не оказывается меньше вуза без
него, а крупнейший получает надбавку, но не доминирование. Для #99 это значит,
что РАН (5 657) и Курчатовский (2 830) считаются от базы своей волны, а не от
этих чисел.

**Что потолок ограничивает.** Отбор *из пула вуза*, а не *подпись на карточке*:
человек из двух пулов, вошедший через вуз без потолка, но с МГУ первым в
`last_known_institutions`, считается МГУ (правило «первый вуз из списка»,
05.09). Поэтому «отобрано под потолком» (1 800 / 1 200) и «подписано как вуз»
(1 721 / 1 165 до дедупликации, **1 714 / 1 163** после) — разные числа, и в
отчёте стоят оба (арифметика — §1 `docs/SFR5c_REPORT.md`).
**Альтернативы:** 1 500 / 1 200 (каталог ≈8,8 тыс., МГУ 17 % — ниже ориентира
#98 «~9–10 тыс.»); 2 000 / 1 300 (≈9,4 тыс., МГУ 21 % — выше ориентира
«18–20 %»); равный потолок всем (отвергнут: десять вузов из двенадцати он бы
не коснулся, а ВШЭ и УрФУ урезал бы без причины).

## 2026-09-26 (SFR-5c) — решения человека о склейках живут в файле, а не в issue

`packages/sfr-match/eval/dedup_decisions.jsonl` — актив в git рядом с
`judgments.jsonl`: одна строка = один вердикт человека о паре профилей
(`ids`, `verdict`, `by`, `date`, `source`, `note`; последние четыре
обязательны — без источника решение неотличимо от догадки агента). Читает
`sfr etl dedup --decisions`; файла нет → предупреждение в stderr, работа по
одним правилам. `sfr etl unmerge` в файл не пишет, а печатает готовую строку:
вердикт вносит тот, кто его принял.

**Почему файл понадобился:** решения по #93, #108, #109 жили в комментариях к
issues, и при каждой пересборке каталога те же четыре пары возвращались в
review, а Jorstad (два ORCID у одного человека) при сборке с нуля ушла бы в
review вместо склейки. Правила ORCID (26.09) знают, чего делать *нельзя*; чего
делать *нужно* в конкретном спорном случае — знает человек.

**Семантика (проговорена до реализации, часть уточнена в разговоре с
советником):**

- **`different`** — пара не оказывается в одной группе **ни по какому сигналу,
  в том числе транзитивно**. Запрет перехватывается там, где сигнал находится
  (в цикле ORCID и в цикле «имя + вуз»), а не фильтруется после union: иначе
  Лукинские снова уехали бы в review как «общая работа при разных ORCID» —
  то есть решение человека было бы учтено только на склейку, но не на список
  «требуют решения».
- Если запрещённая пара всё-таки сходится в одну группу **через третий
  профиль**, вся группа не склеивается и уходит человеку с причиной «запрет
  человека (#N) + третий профиль». Склеивать часть группы нельзя: какой профиль
  чей — знает только он. *Альтернатива, отвергнутая:* выбросить только
  автоматическое ребро и склеить остальное — сложнее, зависит от порядка
  обхода, а выигрыш нулевой (в данных такого случая нет).
- **Один ORCID на группу, внутри которой человек запретил пару**, обезоруживает
  ORCID для всей группы: это тот же класс ошибки источника, что Краева/Кожин.
  Группа из двух — просто пропуск (решение принято), из трёх и больше — в
  review. Найдено при написании тестов: цикл ORCID сравнивает всех с первым
  профилем, и пропуск одного ребра иначе молча склеивал бы остаток группы.
- **`same`** — склейка поверх блокеров, сигнал `human (#N)`, канонический по
  общему правилу (больше работ). Пара, уже склеенная в БД, — no-op, но
  `applied_merges` печатает её сигнал как `human (#N)`, а не «признак не
  восстановить».
- **Конфликт решений** (`same` и `different` в одной группе) — не ошибка файла,
  а строка в review с обоими источниками. Ошибка файла — две строки об одной
  паре, кривой `verdict`, отсутствующие `by`/`date`/`source`: тогда
  `load_dedup_decisions` падает. Молча пропущенная строка означала бы
  потерянное решение человека.
- **Инвариант:** пары с вердиктом `different`, которые в этой БД **уже
  склеены**, печатаются отдельным списком и в review-файл. На `sfr5c.db` он
  пуст, на `sfr5b.db` — три пары (Лукинские, Корянов, Иноуэ). Это механическая

## 2026-09-27 (дедупликация-2) — отпечаток профиля в оценках: устаревшая оценка — неоценённая пара (#123)

Оценка судьи стоит на `author_id`, а после склейки у того же id другой
профиль: у `q17` накопленная разметка держала 1, поставленную профилю
Белогурова до склейки, и Success@1 «упал» без изменения выдачи (§13.5 SFR-5c).
**Решение:** у оценки появляется поле `profile_fp` — 16 hex от sha256
`profile_text`. Судья его не пишет — формат строки задан рубрикой, а рубрику
ради служебного поля не меняем; отпечаток проставляет отдельный шаг `sfr-match
stamp-judgments` по пулу, из которого судили (в строке пула уже есть
`profile_text`). Скрипты метрик сверяют отпечаток с текущим индексом: не
совпал — оценка **устарела**, пара считается неоценённой, число печатается и
пишется в JSON. Строки без отпечатка (вся разметка до 27.09) сверке не
подлежат: это «без отпечатка», а не «устарела», и JSON прошлых отчётов
воспроизводятся байт в байт (блок `staleness` появляется только при строках с
отпечатком). В `sfr5c_three_points.py` оценка для точки отбрасывается, если
устарела относительно базы **или** точки — осторожнее, чем по одной стороне.
`sfr etl dedup` пишет в review-файл оценки на склеенных id (канонический —
профиль меняется, дубль — выбывает), чтобы пересуд был плановым. *(Ревью ветки:
список берёт и уже применённые склейки, поэтому число — верхняя граница; #137.)*
**Альтернатива, отвергнутая:** дописать отпечатки в существующие файлы оценок
задним числом — профили, по которым они ставились, не сохранены, и отпечаток
был бы догадкой; и `n_works` + `built_at` индекса вместо хеша текста — меняется
при пересборке индекса без изменения профиля, то есть устаревали бы и живые
оценки.

**Почему.** Повтор одного состояния и процесса в нескольких входных документах расходился; отчёт, PR и журнал уже сохраняют результаты и основания решений. Свежие факты первого пилота из #60 и уточнения учебного контекста из продуктового чата внесены в единый бриф.

**Альтернативы.** Отдельные праймер и бриф сохраняют две общие вводные; единый файл для паспорта, требований, статуса и истории смешивает разные назначения. Выбраны один компактный вход и ссылки на первичные материалы. Это запись о процессе; она не подтверждает настройку или запуск автоматизации терминала.

## 2026-10-02 — аналитика текущего PoC: PostgreSQL, закрытый контекст и доставка (#162–164)

**Решение Бориса.** После принятого UI-пакета #178 используем PostgreSQL
отдельным внутренним сервисом того же Selectel VPS. Подключение вынесено в
конфигурацию, чтобы позднее перенести БД без изменения модели. Каталог,
SQLite ETL, эмбеддинги и файловый индекс остаются прежними; SFR-7 не запускаем.
Основание — прямая постановка второй технической сессии; исходные issues
уточняются с сохранением происхождения предложений первого пилота.

**Границы сбора.** Полные исходные поисковые запросы сохраняются как материал
для data science, нормализованная строка отдельно. Имена/контакты внутри текста
автоматически не удаляются. Сырые IP, очищенные URL/Referer и разрешённые
диагностические заголовки допустимы только в закрытом исследовательском
слое; эти данные не обезличены. Секреты аутентификации, Cookie,
Authorization, Set-Cookie, X-Revalidate-Secret и секретные URL-параметры
не сохраняются. Явная allowlist/размеры действуют для приложения и прокси.
Нет посимвольного ввода, полного черновика письма, новых форм ПД или
стороннего счётчика. Юридическая готовность этим не установлена (#39).

**Хранение.** Автоматическое удаление по возрасту не вводим. Ротация означает
закрытие и сохранение файла в архиве; повреждённые записи сохраняются для
оператора. Контроль диска, закрытая выгрузка с SHA-256, логический backup и
проверочное восстановление в отдельную БД обязательны. Копия на том же VPS
не защищает от потери VPS; внешний экземпляр предусмотрен на Mac. Старый
архив первого пилота сохраняется без изменения и повторного сбора.

**Идентификация и смысл.** Случайный ID наблюдаемого визита/вкладки в
sessionStorage, отдельные ID попытки поиска, HTTP-запроса и события. Нет cookie
и постоянного идентификатора между визитами. Считаем визиты, не людей;
IP/Referer не используются для связи воронки. Серверный ответ и фактический
показ UI разделены; SSR/prefetch не просмотры. Последовательная воронка
связана одной попыткой; её завершение — успешное копирование письма после
просмотра профиля, без утверждения отправки, ответа или качества подбора.
Время серверов/БД UTC, timestamptz; клиентское время отдельно, задержки
монотонные. Отчёт принимает явный период/часовой пояс, включая Europe/Moscow.

**Надёжная доставка.** Ограниченные таймауты/пул, постоянный дисковый буфер
с подтверждением устойчивой записи и идемпотентной догрузкой после рестарта.
Сбой аналитики не останавливает поиск; приёмник не подтверждает событие,
которое невозможно сохранить. Неполнота и ошибки видимы оператору. Абсолютная
полнота событий при потере сети/закрытии браузера не гарантируется. Отчёты и
выгрузки — команды оператора, публичные исследовательские ручки не нужны.

**Альтернативы.** Одних stdout/Docker-ротаций недостаточно: архив #165 выявил
потерю ранних детальных поисков. SQLite аналитики отклонена прямым решением
Бориса в пользу PostgreSQL. Redis/Kafka/ClickHouse/BI и отдельные микросервисы
для объёма PoC не нужны. Постоянный браузерный ID/аккаунты отложены; модель
оставляет возможность последующего расширения. Предлагавшиеся в #60 30 дней
хранения и в #164 хеширование IP/воронка по Referer не считаются принятыми.

## 2026-10-03 — ограниченный локальный эксперимент ранжирования #17

В рамках отдельного поручения Бориса сравниваются текущий FRIDA и одна
заранее заданная альтернатива RRF FRIDA+BM25 на том же каталоге 9 002.
Параметры/регрессии зафиксированы до сравнения в
`packages/sfr-match/eval/CRITERIA_RANKING17_20261003.md`; бюджет подбора нулевой.
Это не запуск всех задач исторической SFR-7, не расширение #99 и не изменение
production. Старый критерий #17 «100%» остаётся продуктовым вопросом.

Причина выбора: существующий BM25 даёт недорогой проверяемый лексический сигнал;
тяжёлая новая модель и перевод запросов расширили бы эксперимент. Кросс-язычность
и многочастные интересы ограничивают применимость BM25. Историческая гипотеза
«не данные» не принимается за факт; диагностика отделяет порядок от покрытия
кандидатов и неопределённости/неполноты текстов.

Общий слепой пул, новый Astra/max и снимки судимого текста применяются также
к baseline. Старые Fable-оценки не смешиваются. Пилотные примеры обезличены
с происхождением и преобразованиями; это записи, а не подтверждённые независимые
участники/holdout. Гибрид доступен только явным локальным инструментом,
без API confidence: его RRF score не имеет смысла прежнего cosine-порога.
Результат и ограничения передаются через [PR #185](https://github.com/borisboriov/search-for-research/pull/185).

**Решение по результату:** сохранить текущий FRIDA. Продуктовая проверка
подтвердила [измерения](reports/ranking17_20261003.md): у фиксированного гибрида
восемь потерь Success@1/@5 без приобретений; golden24 Success@5 21/24 → 18/24.
Ресурсный фильтр пройден, заранее заданные условия качества — нет.
Альтернатива включить этот гибрид отклонена по результатам одного эксперимента;
это не отказ от любых гибридов или дальнейшего исследования ранжирования.
Новый Astra/max сравнивает оба варианта на одном пуле; исторические Fable-цифры
паспорта сохраняются. Самостоятельного нового основания менять паспорт, питч,
обоснование рынка или Drive этот эксперимент не даёт. Исходные задачи #17/#7
остаются открытыми; следующий эксперимент и изменение их критериев требуют
отдельного решения. Merge и выкладка этим решением не разрешаются.

## 2026-10-11 — контактные карточки v4: дата источника отдельно от current

не нужны: расширены существующие cards/export/import, отдельные source даты и
current неизвестность сохраняются. [Live3 и границы](../enrichment/research/reports/enrichment_night_20261009.md#sol-assisted-live3-и-четыре-человеческих-вопроса--11102026).

## 2026-10-11: модуль enrichment и логическое архивирование без сжатия

**Решение.** Поддерживаемый Sol-assisted runtime выделен в workspace пакет
`enrichment/`, один `sfr-enrichment` CLI. Исторические GLM/night/Pi протоколы
сохранены отдельно, старые entrypoints — адаптеры. Новый freeze хеширует
фактический runtime, packaging/lock и неизменную рубрику. Архивы каталогизированы
ссылками на оригиналы; старые bytes, paths, STOP, human records и seals сохранены.

**Причина.** Смешанные eager imports тянули экспериментальную orchestration,
а 92,9% logical bytes enrichment архивов приходятся на отдельные Pi snapshots
с повтором накопленного текста. Рабочий native путь сохраняет один JSONL, raw,
request/usage/receipt и ошибки. [Карта и измерения](../enrichment/research/INDEX.md)
разделяют объём enrichment и контекст общего SFR checkout.

**Альтернативы.** Новый orchestration framework и изменение алгоритмов не нужны.
Delta-only replay не воспроизводит соседний старый snapshot; сжатие не выбрано
по поручению Бориса. Физический перенос, dedup и удаление старых данных отложены
до отдельного проверенного плана; место этим раундом не освобождено. Результаты
baseline/human/live3 и их продуктовая приёмка не меняются.


## 13.10.2026 — ограниченный автономный merge

По прямому разрешению Бориса проектный hook допускает единственную форму
merge в SFR с полным ожидаемым head SHA, после свежей проверки существующим
