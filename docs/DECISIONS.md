# DECISIONS — журнал решений (ADR-lite)

Формат: дата — решение — почему — альтернативы.

## 2026-08-28 — uv workspace с виртуальным корнем

Корневой `pyproject.toml` без build-system (сам по себе не пакет), два
workspace-пакета `sfr-core` и `sfr-etl` с hatchling. Dev-зависимости — в
dependency-group `dev` корня.
**Почему:** корень не содержит кода; hatchling — стабильный минимальный бэкенд.
**Альтернативы:** uv_build (моложе, меньше документации), setuptools (тяжелее).

## 2026-08-28 — конфиги инструментов в корневом pyproject.toml

ruff/mypy/pytest/coverage настроены один раз в корне, а не по-пакетно.
Разная строгость mypy — через per-module override (`sfr_core.*` strict).
**Почему:** один источник настроек, `make lint`/`typecheck`/`test` работают из корня.
**Альтернативы:** по-пакетные конфиги — дублирование и рассинхрон.

## 2026-08-28 — macOS: UF_HIDDEN на .venv ломает editable-импорты → `make unhide`

На macOS uv помечает содержимое `.venv` флагом `UF_HIDDEN`, а CPython (3.13 и
бэкпорт в 3.12.13) пропускает hidden `.pth`-файлы в site-packages — editable-пакеты
workspace молча перестают импортироваться (`ModuleNotFoundError: sfr_core`).
**Решение:** цель `unhide` в Makefile (`chflags -R nohidden .venv`), прогоняется перед
всеми uv-командами; на Linux/CI — no-op. Плюс пин Python 3.12 (`.python-version`) —
версия из SPEC и CI.
**Альтернативы:** не-editable установка (`--no-editable`) — неудобно при разработке;
PYTHONPATH-хаки — маскируют проблему.

## 2026-08-28 — сверка с реальным OpenAlex API (пробные запросы)

Расхождения со SPEC/ожиданиями, зафиксированные по фактическим ответам:

- У Institution **нет поля name_ru**: русское название лежит в
  `display_name_alternatives` (у МФТИ `international.display_name.ru = null`).
  Решение: `name_ru` = первая кириллическая строка из `display_name_alternatives`, nullable.
- У Author `last_known_institutions` — **список** (у одного автора до 3+ институтов),
  а не единственный FK. Решение: в БД храним один FK — целевой институт ингеста
  (тот, по которому автор был найден); полный список остаётся в `raw` JSON.
- Метрики автора лежат в `summary_stats` (`h_index`, `i10_index`, `2yr_mean_citedness`).
- Фильтр авторов по вузу: используем `last_known_institutions.id:<ID>` (у МФТИ 7649
  авторов) — «текущая» аффилиация релевантнее для подбора НР, чем историческая
  `affiliations.institution.id`. Сортировка `works_count:desc`, cursor-пагинация
  (`meta.next_cursor`) — подтверждены.
- Работы: `abstract_inverted_index` (nullable), `topics[].score`, `title == display_name`,
  параметр `select=` работает — используем для сокращения трафика.
- «Свежесть» публикации автора на этапе ингеста авторов определяем по `counts_by_year`
  (годы с `works_count > 0`), т.к. работ в БД ещё нет; порядок элементов не гарантирован —
  фильтруем по значению года. «Последние N лет» = календарные годы `>= current_year - N + 1`.
- Данные: топ по works_count — участники мегаколлабораций (напр. «A. Zhemchugov»,
  2847 работ, h=152, 100+ соавторов на работу) — кандидаты в проблемы качества для REPORT.

## 2026-08-28 — coverage: исключены CLI-обвязка и alembic

`omit = ["*/sfr_etl/cli.py", "*/alembic/*"]` — порог ≥80% считается по чистой
логике, как требует §5 SPEC («не считая CLI-обвязку и alembic»).

## 2026-08-28 — Work: составная уникальность (author_id, openalex_id), а не по openalex_id

Одна и та же работа законно попадает в профили нескольких кандидатов (соавторство
внутри вуза: на прогоне — 351 такая работа).
**Почему:** SFR-0 хранит связку «в чьём профиле учитываем» (§3 SPEC), а не полную
many-to-many авторство; уникальность только по `openalex_id` теряла бы работу у
всех соавторов, кроме первого.
**Альтернативы:** отдельная таблица authorship — избыточно для SFR-0.

## 2026-08-28 — отбор работ: половина бюджета цитируемым, половина свежим

`merge_work_records`: `ceil(per_author/2)` самых цитируемых + свежие до лимита,
дедупликация по id, добор цитируемыми, если свежих мало.
**Почему:** профиль должен отражать и вес учёного (цитируемость), и то, чем он
занят сейчас (для подбора НР это важнее). Два запроса на автора вместо одного —
приемлемая цена (523 запроса на 261 автора).
**Альтернативы:** только цитируемые (профиль «замораживается» на старых хитах),
только свежие (теряется вес).

## 2026-08-28 — «свежесть» автора считается по counts_by_year, а не по работам

На шаге `etl authors` работ в БД ещё нет, поэтому `is_supervisor_candidate`
использует `counts_by_year` из ответа API (годы с `works_count > 0`).
**Почему:** иначе шаги пришлось бы связать в один проход и потерять
идемпотентность/кэшируемость по отдельности.
**Альтернативы:** пересчёт флага после ингеста работ — можно добавить в SFR-1,
если пороги начнут крутиться.

## 2026-08-28 — AuthorTopic.score = topics[].count, x_concepts не используются

**Почему:** `x_concepts` помечены OpenAlex как deprecated; `topics[].count` —
число работ автора по теме, устойчивый признак специализации.
**Альтернативы:** `topic_share` (доля) — менее интерпретируемо в отчёте.

## 2026-08-28 — ручной разбор отчёта вынесен в docs/REPORT_notes.md

`sfr report` перегенерирует `docs/REPORT.md` целиком, поэтому написанный руками
разбор и DoD-чеклист хранятся отдельно и подклеиваются генератором в конец.
**Почему:** иначе любая перегенерация стирала бы человеческую часть §7.
**Альтернативы:** править REPORT.md руками после каждой генерации — рассинхрон.

## 2026-08-28 — run_stats хранит историю прогонов, а не последний

`data/run_stats.json` — список записей на шаг; отчёт показывает первый (холодный)
и последний (кэшированный) прогоны.
**Почему:** DoD прямо спрашивает про «повторный прогон почти не ходит в сеть» —
для этого нужны обе точки, а перезапись затирала холодные цифры.

## 2026-08-28 — ruff: отключены RUF001–RUF003 (ambiguous unicode)

Проект двуязычный: русские строки в CLI-выводе, отчёте и profile_text — норма,
а правила ловят кириллицу как «похожую на латиницу».
**Альтернативы:** `# noqa` в каждой строке — шум.

## 2026-08-29 (SFR-1) — отдельный пакет `sfr-match`, а не расширение `sfr-etl`

Третий workspace-пакет `packages/sfr-match` (`src/sfr_match/`), зависит от `sfr-core`.
**Почему:** NEXT.md предлагал «`sfr-ml` или расширение sfr-etl»; мэтчинг — будущий
продуктовый модуль (его же будет звать FastAPI в SFR-2), а ETL — офлайн-инструмент.
Смешивать их значит тащить httpx/tenacity в рантайм API, а torch — в ETL-контейнер.
**Альтернативы:** расширение sfr-etl (быстрее, но неверная граница ответственности).

## 2026-08-29 — русско-специализированная модель: `ai-forever/FRIDA`

§3.3 SPEC_SFR1 требует модель из топа ruMTEB (retrieval) < 1.5B. Взята FRIDA
(823M параметров, FRED-T5-энкодер, префиксы `search_query: ` / `search_document: `).
**Почему:** топовая по ruMTEB модель, укладывающаяся в лимит: лидер лидерборда
GigaEmbeddings — 7B+, вне лимита. Доступность проверена через HF API
(`gated: false`), модель грузится в sentence-transformers 6.0 и отдаёт dim=1536.
**Альтернативы:** `ai-forever/ru-en-RoSBERTa` (404M, билингвальная — запасной вариант,
если бы FRIDA не загрузилась), `deepvk/USER-bge-m3` (359M), `sergeyzh/BERTA` (128M).
**Риск, зафиксированный заранее:** карточка FRIDA прямо пишет, что модель заточена
под русский, а качество на английском неизвестно — а корпус профилей в основном
англоязычный. Это и меряем.

## 2026-08-29 — FAISS пишет индекс, поиск считает NumPy (конфликт libomp на macOS)

`faiss-cpu` и `torch` линкуют по своей копии libomp; на macOS второй инициализатор
роняет процесс (`OMP: Error #15`) ровно на `IndexFlatIP.search`. Порядок импорта не
спасает, `omp_set_num_threads(1)` тоже; единственный переключатель
`KMP_DUPLICATE_LIB_OK=TRUE` сам upstream описывает как способный «silently produce
incorrect results».
**Решение:** FAISS пишет `index.faiss` (артефакт для SFR-2), рядом кладётся
`vectors.npy`; поиск — точный NumPy-скан по внутреннему произведению. На 261 профиле
это точно и занимает доли миллисекунды. Равенство двух путей проверяется тестом
`test_numpy_scan_matches_faiss_exactly`. Сборка индекса (torch + faiss в одном
процессе) безопасна при порядке «сначала эмбеддер, потом faiss» — так и сделано.
**Почему не «выкинуть FAISS»:** §2 SPEC_SFR1 требует FAISS-индекс, и в проде (Linux)
конфликта нет — формат хранения должен быть тот, с которым поедет SFR-2.
**Альтернативы:** `KMP_DUPLICATE_LIB_OK=TRUE` (риск молча неверных чисел в
эксперименте, чей единственный результат — числа); считать эмбеддинги и поиск в
разных процессах (усложняет CLI ради машины разработчика).

## 2026-08-29 — clean-варианты построены для всех моделей, а не только для лучшей

§5 SPEC_SFR1 просит прогнать в clean/no-clean лучшую модель. Построены оба варианта
для всех пяти.
**Почему:** судейский пул собирается один раз по объединению топ-5 всех прогонов;
если clean-вариант добавить после разметки, придётся доразмечать вторым раундом —
и часть пар будет оценена в другом контексте. Дешевле проиндексировать вдвое больше
(261 профиль), чем получить неоднородную разметку.

## 2026-08-29 — `paraphrase-multilingual-mpnet-base-v2` оставлен с `max_seq_length=128`

Модель обрезает вход на 128 токенах — это меньше, чем profile_text (до 1500 символов).
Лимит не поднимался.
**Почему:** 128 — то, на чём модель обучалась и как она поставляется; поднять окно
значит мерить не ту модель, которую кто-то возьмёт «из коробки». Ограничение
зафиксировано в отчёте как объяснение результата, а не спрятано.

## 2026-08-29 — судейство: пул топ-5, сортировка по author_id, неоценённые = grade 0

Пул — объединение топ-5 всех 10 вариантов; пары сортируются по `(query_id, author_id)`,
а не по score, чтобы судья не видел, какая модель их выдала. Пары в топ-10, не попавшие
в пул, считаются нерелевантными при расчёте nDCG@10.
**Почему:** стандартная практика pooled evaluation (TREC): полная разметка 30×261
невозможна, а «неоценённое = 0» одинаково штрафует все модели. Доля оценённых пар
в топ-5 выводится в отчёт отдельной таблицей — чтобы видно было, где оценка неполна.

## 2026-08-29 — CLI: сверх четырёх команд §2 добавлены `pool`, `review-sample`, `stats`

`pool` выгружает пул пар для судейства, `review-sample` пишет `judgments_for_review.md`,
`stats` показывает, что меняет чистка на текущем корпусе.
**Почему:** §5 требует и пул, и файл на ручную проверку; делать их разовыми скриптами
значит потерять воспроизводимость `make eval`.

## 2026-08-29 — рубрика судейства: grade 2 = «покрыто главное содержание запроса»

На составных запросах (например q07 «deep learning для физики частиц») буквальное
«прямое совпадение специализации» не встречается ни у кого. Принято правило: grade 2
ставится, если профиль покрывает то, ради чего студент ищет НР, а не любую половину
формулировки. Для q07 это данные с детекторов (метод студент приносит сам), поэтому
экспериментаторы ATLAS/CMS получили 2, а «чистые» ML-специалисты — 1.
**Почему:** иначе либо ни один запрос не имеет grade=2 (метрика вырождается), либо
grade=2 получает всё подряд (метрика перестаёт различать модели).
**Альтернатива:** отдельные оценки по каждой половине запроса — усложняет разметку
вчетверо ради запросов, которых 1–2 на набор.

## 2026-08-29 — два out-of-domain запроса оказались in-domain; порог не перекалиброван

q27 («история России XIX века») нашёл М. С. Горбачёва с темой «Soviet and Russian
History», q29 («выпечка хлеба») — В. В. Иванова с темой «Food Industry» и работой про
экструдированные зерновые хлебцы. Оценки выставлены честно (1 и 2), запросы оставлены
в наборе с прежним ярлыком `out-of-domain`.
**Почему не переклассифицировать:** ярлык фиксирует замысел составителя, а не
результат; переписать его задним числом — подогнать набор под ответ. Расхождение
разобрано в отчёте как ограничение методики, а порог 0.35 честно помечен как
стоящий на двух точках (q28, q30).
**Следствие для SFR-2:** нужен отдельный набор из ≥15 заведомо посторонних запросов.

## 2026-08-29 — чистку profile_text оставляем включённой, несмотря на нулевой эффект

Clean меняет 46 из 261 профилей (медиана 30 символов) и сдвигает Success@5 на ±1
запрос в разные стороны у разных моделей — то есть в пределах шума.
**Почему не выключаем:** чистка ничего не стоит на индексации, делает выдачу читаемой
для человека (профили пойдут на сайт в SFR-2) и снимает мусор, который иначе всплывёт
при росте корпуса.
**Что это значит для SFR-0:** проблемы №1–2 из REPORT.md оказались менее важными,
чем предполагалось — 2% текста не двигают эмбеддинг.

## 2026-08-29 (SFR-2) — карточки НР отдаются без авторизации

`/api/match` и `/api/supervisors/{id}` возвращают полную карточку (имя, вуз, h-index,
works_count, темы, profile_text) любому клиенту, без токена и без урезания полей.
**Почему:** это не техническое упрощение, а продуктовое решение из плана MVP v1.3 —
карточки открытые и бесплатные, монетизация строится на сервисах вокруг данных
(сопровождение, аналитика для вузов), а не на самих данных. Прятать за авторизацией
то, что уже открыто в OpenAlex, значит создавать трение без выручки.
**Следствие:** авторизация не появляется и в SFR-3; если продуктовое решение
изменится, менять придётся и контракт API, и фронт.

## 2026-08-29 (SFR-2) — бэкенд поиска выбирается по платформе

`select_search_backend()`: FAISS везде, кроме macOS, где faiss и torch конфликтуют
по libomp (разбор — в `runtime.py` и в решении от 29.08 про NumPy-скан). Переключатель
`SFR_SEARCH_BACKEND=faiss|numpy` перекрывает автоматику.
**Почему не «FAISS везде»:** конфликт на macOS не лечится, а разработка идёт на macOS.
**Почему не «NumPy везде»:** на 535 профилях разницы нет, но файловый IndexFlatIP —
это задел под рост корпуса, и проверять его надо там, где он будет работать.
**Оговорка, которую нашёл тест:** на точных ничьих порядок расходится — NumPy
разрешает их по индексу (stable sort), FAISS нет. Поэтому эквивалентность
проверяется как «те же документы + те же score», а порядок — только там, где
score различаются. На живых 1536-мерных векторах ничьих не бывает, но на
вырожденных данных (и в юнит-тестах с фейковым эмбеддером) бывают.

## 2026-08-29 (SFR-2) — корпус 535 профилей, индекс с включённой чисткой

API и все эксперименты SFR-2 работают на `profiles_mipt_msu.jsonl` (535 профилей
МФТИ+МГУ), индексы собираются с `--clean`.
**Почему:** решение SFR-1 «чистку оставляем включённой» касалось именно этого шага;
корпус двух вузов — последнее измеренное состояние, и откатываться к 261 профилю
одного вуза ради сравнимости с первой таблицей SFR-1 значит показывать продукт хуже,
чем он есть.
**Цена:** бейзлайн композиции (`frida_clean`, полный текст) не совпадает с цифрами
МГУ-прогона из SFR-1 — тот был на сыром тексте. Сравнение внутри эксперимента
однородно, а расхождение с SFR-1 оговорено в отчёте.

## 2026-08-29 (SFR-2) — наборы запросов разведены по файлам, SFR1_REPORT.md заморожен

`queries.jsonl` (golden, 30) остаётся неизменным; новые посторонние запросы живут
в `ood_queries.jsonl`, будущие студенческие — в `external_queries.jsonl`.
**Почему:** дописать 15 запросов в `queries.jsonl` было проще, но `sfr-match report`
перезаписывает `docs/SFR1_REPORT.md` целиком, а nDCG и MRR считаются против
размеченного пула — выросший пул задним числом сдвинул бы уже опубликованные цифры,
на которые ссылается правка паспорта. Success@k этим не страдает, nDCG страдает.
**Что с этим делать дальше:** `make eval` (цепочка SFR-1) не запускать без нужды;
воспроизведение SFR-2 — это `make eval-sfr2`, оно пишет отдельный отчёт.

## 2026-08-29 (SFR-2) — карточка всегда показывает полный очищенный профиль

В `docs.json` рядом с индексируемым текстом лежит `display_text` — очищенный
`profile_text` целиком, независимо от того, что попало в индекс.
**Почему:** состав индекса — вопрос качества поиска, а состав карточки — вопрос
того, что человек читает, и это разные вопросы. Если эксперимент §5 покажет, что
в индекс достаточно класть темы, карточка от этого не должна превратиться в две
строки. Обратное тоже верно: показывать сырой текст с LaTeX-мусором нельзя,
хотя в индексе он почти ничего не меняет (измерено в SFR-1).

## 2026-08-29 (SFR-2) — torch на Linux ставится с CPU-индекса PyTorch

В корневом `pyproject.toml` объявлен `[[tool.uv.index]] pytorch-cpu` и источник
`torch = [{ index = "pytorch-cpu", marker = "sys_platform == 'linux'" }]`; сам
`torch` добавлен в зависимости `sfr-match` явно (иначе источник не к чему привязать).
**Почему:** первый собранный образ весил **10.3 ГБ** — в нём лежали CUDA-колёса
(`nvidia-*`, `triton`), которых на CPU-VPS не будет никогда. После правки — **2.4 ГБ**.
Это прямо влияет на выбор хостинга: 10 ГБ образа требуют другого тарифа по диску.
**Почему через marker, а не глобально:** на macOS у CPU-индекса нет колёс, разработка
там бы сломалась.

## 2026-08-29 (SFR-2) — порог отсечки принадлежит варианту индекса, а не проекту

Калибровка считается по `frida_clean` (полный profile_text) — тому варианту, который
реально обслуживает API.
**Почему:** score — это косинус между запросом и текстом профиля; если в индексе
лежат только темы, распределение score другое, и порог, снятый с полного текста,
на нём ничего не значит. Эксперимент §5 отвечает на вопрос «что класть в индекс
дальше», а не «что стоит в проде сейчас», поэтому порог калибруется на текущем прод-варианте.
**Следствие:** если по итогам эксперимента состав индекса поменяется — порог придётся
калибровать заново, и это надо будет написать в отчёте, а не унаследовать число.

## 2026-08-29 (SFR-2) — модель не запекается в образ, «холодный старт» считается без скачивания

Dockerfile не содержит весов; HF-кэш монтируется томом (`HF_HOME=/models`), при замере
ресурсов — bind-mount хостового кэша.
**Почему:** FRIDA — это ~2 ГБ поверх образа, они не меняются между релизами кода,
и запекать их значит гонять их при каждом деплое. Плюс переключение модели
(`SFR_API_MODEL=mpnet`) не должно требовать пересборки образа.
**Как это влияет на цифру:** «холодный старт» в отчёте — это загрузка модели с диска
в память, без сетевого скачивания. Первый в жизни запуск на пустом томе будет дольше
на время скачивания; это оговорено в отчёте.

## 2026-08-29 (SFR-2) — версия индекса как явное поле, а не «доверимся каталогу»

`IndexMeta` получил `compose`, `built_at` и `corpus_sha` (sha256 по id + индексируемым
текстам); производное `version` вида `frida_clean-535p-abe35971` отдаётся в `/api/health`
и в каждом ответе `/api/match`.
**Почему:** индекс собирается офлайн и монтируется в контейнер — то есть API и индекс
живут отдельными жизнями и могут разъехаться молча. Хэш корпуса ловит именно это:
одинаковое имя каталога при разном содержимом. Поля добавлены со значениями по
умолчанию, поэтому индексы SFR-1 продолжают читаться.

## 2026-09-03 (SFR-3) — обогащение карточек: отдельный офлайн-артефакт, а не пересборка индекса

Странице НР нужны цитирования и список работ, а `docs.json` индекса их не несёт;
email и должность в каталоге отсутствуют вовсе. Введён `data/exports/cards.jsonl`
(`sfr export cards` / `make export-cards`): author_id → `cited_by_count` из БД +
топ-10 работ тем же алгоритмом «цитируемые, потом свежие», что и `profile_text`
(`select_works_for_profile`) — человек читает те же работы, что видела модель.
API подхватывает файл на старте (`SFR_API_CARDS_PATH`), при его отсутствии поля
пустые, а не ошибка. `position`/`email` объявлены в контракте, но всегда `null`:
данных нет, парсить новое запрещено (SPEC_SFR3 §4).
**Почему не пересборка `docs.json`:** это часы эмбеддинга и риск сдвинуть
воспроизводимость SFR-2 ради полей, не влияющих на поиск.
**Альтернативы:** читать БД из API (тащит SQLAlchemy в рантайм сервиса);
дописать поля в `profiles_mipt_msu.jsonl` (меняет замороженный корпусный файл).

## 2026-09-03 (SFR-3) — npm, а не pnpm; Node 24 LTS

npm идёт с Node, в CI не требует отдельной установки, lock коммитится.
Скорость pnpm на одном маленьком приложении ничего не решает. `.nvmrc` = 24
(LTS; локальная Node 26 тоже подходит, `engines >= 24`).

## 2026-09-03 (SFR-3) — ISR (revalidate 1 час), а не SSG на билде

Страницы НР рендерятся на сервере по требованию и кэшируются на час;
`generateStaticParams` пуст. **Почему:** SSG на билде требует живого API на
билд-машине (в CI его нет — сборка обязана проходить без бэкенда) и фиксирует
каталог моментом сборки. Каталог меняется раз в семестр — час устаревания
ничем не грозит, а первый запрос к странице (~200 мс TTFB) незаметен.
Лендинг и sitemap — тот же revalidate 3600.

## 2026-09-03 (SFR-3) — клиентские запросы через прокси /api/match Next.js

Браузер ходит только на свой origin; route handler переправляет на
`SFR_API_URL`. Внутренний адрес API не светится, CORS в проде не нужен
(CORS-настройка в API остаётся для локальной разработки без прокси).
Падение бэкенда конвертируется в 502 с человеческим текстом.

## 2026-09-03 (SFR-3) — деградация вместо выдуманных чисел при недоступном API

Сборка и рендер обязаны работать без бэкенда: полоса цифр лендинга прячет
счётчик профилей (2 вуза и «100% открытые данные» — статические факты),
превью подборки скрывается, sitemap отдаёт только лендинг. Ошибка сети на
`/results` — отдельное состояние с «Повторить». Правило спеки «формулировки
по макету, но без выдуманных чисел» распространено и на отказ API.

## 2026-09-03 (SFR-3) — блок «NN% совпадение» как клиентский островок

под Suspense. Чтение searchParams в серверном компоненте сделало бы страницу
динамической и убило бы ISR. Значение вне (0, 1] просто не рендерится.
