# eval/ — наборы запросов и судейство

Здесь лежат **входы** (наборы запросов, оценки, рубрика, критерии, решения
человека) и **доказательства** — review-файлы, на которые отчёт или
`docs/DECISIONS.md` опираются как на основание утверждения. Всё остальное, что
пишут цели и CLI, — в gitignored `data/eval/review/` (правило — `docs/DECISIONS.md`
27.09, «чистка eval», #143).

## Как собрать внешний тест-сет (инструкция для Бориса и Светы)

**Зачем.** Все 30 запросов golden set написал агент, прочитав топ-15 тем корпуса.
Это значит, что набор подогнан под данные: он меряет не продукт, а совпадение
выборки запросов с выборкой профилей. Реальные студенты спрашивают иначе, и доля
«ничего не нашли» у них будет выше. Пока внешнего набора нет, все цифры качества
(Success@5, Success@1) — цифры на своём же поле.

**Главное правило: не показывать корпус.** Ни список тем, ни имена НР, ни примеры
удачных запросов. Иначе получится то же самое смещение, только чужими руками.

**Как спрашивать.** Просьба формулируется одной фразой:

> «Опиши в 1–3 предложениях, чем ты хочешь заниматься в магистратуре/аспирантуре —
> так, как объяснил бы другу. Не подбирай научные термины специально.»

Годится всё: и узкое («безнейтринный двойной бета-распад»), и широкое
(«что-нибудь про ИИ в медицине»), и кривое, и с опечатками. Плохие и размытые
запросы **особенно ценны** — на них проверяется порог «мы никого не нашли».

**Сколько.** 10–15 запросов от разных людей. Лучше 10 честных, чем 15 с двумя
придуманными: выдуманный запрос возвращает нас к той же подгонке.

**Что записать про каждый.** Только текст запроса и курс/направление автора
(без ФИО — набор уходит в git). Если человек описал интерес голосом — записать
дословно, не причёсывая формулировку.

**Куда положить.** В этот файл — `packages/sfr-match/eval/external_queries.jsonl`,
по одному JSON-объекту на строку:

```json
{"id": "e01", "text": "хочу заниматься ИИ в медицине, что-то про снимки", "expect": "in-domain", "source": "student", "comment": "2 курс бакалавриата, ФПМИ"}
```

- `id` — `e01`, `e02`, … (уникальные);
- `expect` — ожидание составителя: `in-domain` (в каталоге такой НР,
  вероятно, есть), `out-of-domain` (вероятно, нет), `edge` (короткий, с опечатками,
  на стыке тем). Ошибиться здесь не страшно: это гипотеза, а не оценка;
- `source` — всегда `"student"`;
- `comment` — курс и направление, без имени.

**Что дальше сделает агент.** Прогонит набор через `sfr-match eval --queries external`,
разметит пары по той же рубрике, посчитает Success@1/@5 отдельно по внешнему набору
и сравнит с golden set. Расхождение и будет честной оценкой того, насколько
завышены нынешние цифры.

## Локальный эксперимент ранжирования #17

Протокол — [CRITERIA_RANKING17_20261003.md](CRITERIA_RANKING17_20261003.md).
Новый обезличенный набор
[pilot_queries_ranking17_20261003.jsonl](pilot_queries_ranking17_20261003.jsonl)
содержит записи пилота с происхождением/преобразованиями. Он диагностический,
не независимый holdout; frozen-наборы выше не меняются. Предполагаемый ответ
команды исключён, влияние гайда и число независимых участников не подтверждены.

`scripts/ranking_experiment.py` запускает только локальный uncached поиск:
baseline FRIDA и явный эксперимент RRF FRIDA+BM25, три повтора в отдельных
процессах. API, confidence, production и исходный индекс не меняются.
Пути входов задаются явно; все выходы требуют нового имени. Полный путь
включает API validation и embedding, без HTTP, карточек, очереди и кэша.

```bash
OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 \
TOKENIZERS_PARALLELISM=false uv run --locked python scripts/ranking_experiment.py run \
  --index-dir /absolute/path/to/data/indexes_sfr5c/frida_clean \
  --queries packages/sfr-match/eval/queries.jsonl \
    packages/sfr-match/eval/ood_queries.jsonl \
    packages/sfr-match/eval/external_queries.jsonl \
    packages/sfr-match/eval/pilot_queries_ranking17_20261003.jsonl \
  --out-dir /absolute/path/to/new-comparison
```

Пул `blind_pool.jsonl` сортируется по query_id/author_id и скрывает вариант,
rank, score, expect и прежнюю разметку. Судья — отдельный Astra/max по рубрике;
author не заменяет его. В новую оценку переносится отпечаток **судимого текста**
`profile_fp` и полный `profile_hash` из пула. Это отличается от отпечатка
исходного profile_text индекса, если display_text очищен/дополнен: сравнение
проводится с тем же слепым снимком, а не с другим представлением профиля.
Поле `alternate_grade` хранит только сомнение самого судьи по той же шкале.

```bash
uv run --locked python scripts/ranking_experiment.py measure \
  --out-dir /absolute/path/to/comparison \
  --judgments /absolute/path/to/new-judgments.jsonl \
  --out /absolute/path/to/new-metrics.json
```

Неоценённые/устаревшие пары, иной судья, различающиеся входы или нестабильные
повторы блокируют расчёт. Success@k и спорные интервалы выводятся отдельно
по группам; RRF score не интерпретируется по прежним cosine-порогам.

## Отпечаток профиля в оценках (#123)

Оценка стоит на паре (запрос, `author_id`) и относится к профилю **на момент
судейства**; после склейки у того же id другой `profile_text`. Поэтому после
каждого прогона судьи оценки получают отпечаток профиля — отдельным шагом, по
тому же пулу (формат строки судьи задан рубрикой и не меняется):

```bash
uv run sfr-match stamp-judgments --pool data/eval/pool_<прогон>.jsonl \
    --judgments packages/sfr-match/eval/judgments_<прогон>.jsonl
```

Скрипты метрик (`sfr5c_deploy_metrics.py` с `--index-root`,
`sfr5c_three_points.py`) сверяют отпечаток с текущим индексом: оценка, чей
профиль изменился, **не берётся** — пара считается неоценённой, число таких
пар печатается. Строки без отпечатка (все прогоны до 27.09.2026) сверке не
подлежат и учитываются как раньше. `sfr etl dedup` выводит в review-файл
список оценок, которые склейки делают устаревшими.

## Чтение рубрики — решения человека

Спорные чтения шкалы решает Борис по выборкам итераций, решения переносятся в
`JUDGE_RUBRIC.md`, раздел «Уточнения чтения шкалы» (двухчастные запросы,
статьи коллабораций, смежная область — #112, 26.09.2026). Проверка случайных
выборок: SFR-5b — #94 (31 пара, одна поправка); SFR-5c — 13 пар из 13,
0 несогласий, партия принята без пересуда (#112, 26.09.2026; порог из спеки —
≥3 несогласий из 13); у SFR-5 отдельной проверки не было (#4 закрыт как
перекрытый #94).

**Как это называть рядом с цифрой качества** (#128): «оценки ставит модель;
человек проверяет выборки и решает спорные чтения шкалы». Не «человеческого
судейства нет»: три уточнения 26.09 приняты по запросам этого же golden set
(`q08`, `q17`, `q25`) и прямо определяют их оценки.

## Сохранённые запросы /match как источник кандидатов

Полные поисковые запросы нужны для data science, но могут содержать имена,
контакты и другие личные сведения. Солёный `ip_hash` **не делает текст запроса
обезличенным**. Совместимый JSONL успешных `/match` по-прежнему пишется в Docker
stdout; его ротация не гарантирует сохранность истории. Основные источники —
PostgreSQL и устойчивый закрытый журнал аналитики. До выкладки этого слоя
исторические журналы сохраняются и анализируются как приватные данные.

Оператор выгружает данные в закрытый файл, без вывода запросов в терминал:

```bash
# Подключение reader задаётся окружением, не аргументами команды.
# Из корня репозитория; CLI создаёт каталог 0700 и файл 0600, не затирает существующий.
make analytics-export ANALYTICS_ARGS="--format match-jsonl --out data/analytics/match-candidates.jsonl"
```

Для Compose без опубликованного порта БД — `analytics-operator export` по
[эксплуатационной инструкции](../../../deploy/README.md#отчёт-диагностика-и-закрытая-выгрузка).
`match-jsonl` сохраняет совместимые поля успешных запросов и нормализованный
`query`; исходный текст до `strip`, ошибки и связанный контекст доступны в
закрытом JSON schema-v1. Кандидаты `none`/`weak` полезны для проверки порогов;
`expect` остаётся гипотезой разбирающего, а не доказанной оценкой пользователя.

Raw-файлы не включать в git, issues, PR или публичные отчёты. Перенос в
`external_queries.jsonl` разрешён только после проверки каждого кандидата и
подготовки обезличенного текста: убрать персональные сведения и уникальные
детали, которые идентифицируют автора. Приватный оригинал сохраняется отдельно.
Если формулировка изменена, отметить обезличивание в `comment`; не выдавать
такой пример за дословный запрос. Для публичного набора предпочтительнее
отдельно собранные запросы по инструкции выше; перед записью их текста в git
также проверить отсутствие личных сведений.
