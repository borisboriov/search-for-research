# AGENTS.md — Search For Research

Общие правила Codex и Claude Code. `CLAUDE.md` импортирует этот файл;
процедуры находятся в `.agents/skills/`, без копий в инструкциях клиентов.

## Вход и роли

1. Прочитать `docs/product/brief.md`: единая вводная и принятое состояние.
2. Прочитать постановку, связанные issues/PR и свежие решения по теме.
   В `docs/DECISIONS.md` — причины решений; весь журнал читать не нужно.
3. По задаче открыть требования, отчёт и артефакты из `docs/README.md`.
   Перед возобновлением старого чата заново проверить ветку, PR и их состояние.

**Авторская сессия** обновляет порученный ей основной материал и его ссылки.
**Продуктовый поток** принимает общие решения и обновляет принятое состояние.
**Технический поток** реализует поручение и передаёт доказательства. Роль определяется поручением,
а не моделью или приложением. Автономный технический агент не редактирует
`docs/product/` и паспорт без прямого поручения Бориса или передачи этой
работы из продуктового потока. Он предлагает изменения в PR/issue.

Использовать файлы текущего checkout. Ссылки на другой checkout не означают,
что его изменения уже в main или на сервере. Архивные спеки — история;
спека открытой итерации находится в корне, конкретное поручение определяет scope.
Название будущей итерации и запись на доске не разрешают её начать.

## Цикл работы

Выбрать маршрут по поручению; процедуры читать только на нужном этапе:

| Событие | Действие |
|---|---|
| Обсуждение без изменения артефактов | Ответить в чате; не создавать файлы, задачи или PR ради процесса |
| Исследование / продуктовые документы | Обновить существующий основной материал: выводы, источники, допущения и открытые вопросы; общие документы — при принятом общем решении |
| Код / данные / эксперимент | Выполнить постановку, сохранить версии и доказательства, пройти профильные проверки |
| Передача поручения или ведение задачи | `.agents/skills/sfr-session-prompt/SKILL.md`; для issues и доски — `.agents/skills/issues/SKILL.md` |
| Передача изменённого результата | Независимое ревью PR — `.agents/skills/review-iteration/SKILL.md`; приёмка и завершение — `.agents/skills/sfr-verify-session/SKILL.md`, `.agents/skills/sfr-close-round/SKILL.md` |
| Сообщение о merge | Проверить факт и один раз завершить разрешённый раунд по `sfr-close-round`; выполненное не повторять |

Продолжение без новых фактов не запускает повторную ревизию. Общая проверка
нужна при противоречии источников, изменении общей границы или подготовке сдачи;
обычно достаточно сверить затронутые связи. Состояние — в существующем
материале/issue/PR, без нового журнала или расписания.

Новый отдельный чат/CLI-сессия запускается по прямой просьбе Бориса;
субагенты для реализации и ревью разрешены в рамках поручения. Сообщения
в другой чат и повторные задания ему — в пределах разрешённого цикла.
Техническую CLI-сессию в PyCharm запускает Борис вручную; продуктовый поток
готовит постановку и затем сопровождает разрешённый цикл через PR.
Не управлять терминалом через Computer Use. Само чтение правил ничего не запускает.

Для изменений репозитория работать в собственной ветке; параллельно — в отдельном
worktree. Локальный документ не требует искусственного PR. Не переключать чужой checkout. Перед
продуктовыми правками в ветке технической сессии остановить её запись.
Черновой PR открыть достаточно рано для CI. До передачи результата:
независимый ревьюер → исправления → повторная проверка затронутых изменений →
CI актуальной версии. Подтверждение ревью с base/head хранить в PR;
старый зелёный запуск и раздел с заголовком «ревью» не доказывают готовность.
При разрешённом фоновом сопровождении связь PR с продуктовым чатом и
порядок повторных проверок задаёт `sfr-session-prompt`; не создавать второй
монитор той же работы или постоянные файлы состояния.

## Разрешения и доступ

Уже разрешённые действия выполнять без повторных вопросов; новое продуктовое
решение или расширение scope требует решения Бориса, а не нового общего аудита.
В рамках поручения разрешены чтение, правки, зависимости по lock, проверки,
своя ветка, коммиты, явный `git push -u origin <своя-ветка>`, свой PR,
issues и синхронизация доски. Merge разрешён в явно порученном цикле только точной командой
`gh pr merge --repo borisboriov/search-for-research N --merge --match-head-commit SHA`
после актуального независимого ревью, ready-приёмки и checks/web/audit,
проверенных проектным live gate. Это не разрешает начинать новые задачи.
Push в main/master, force/delete,
переписывание истории, деплой, удаление данных и глобальная конфигурация —
по отдельной прямой команде Бориса. Исключение: Борис заранее разрешил
продуктовому потоку после своего сообщения о merge удалить полностью влитые
ветки и завершённые worktree этого раунда без повторного вопроса — только
после проверок принадлежности, прекращения работы и сохранности результатов
по `sfr-close-round`. Блокировка среды — не разрешение её обходить.

Репозиторий `borisboriov/search-for-research`, доска
<https://github.com/users/borisboriov/projects/5>. Использовать `gh` с явным
`--repo borisboriov/search-for-research` сразу после подкоманды. Многострочный
текст передавать через `--body-file`. Доступ локальных сессий использует
macOS Keychain; сетевой отказ не означает, что нужен повторный login.
Не выводить токены, приватные ключи, `.env`, credential helper и необработанные
remote URL; не переносить credentials в git, промпты и документы.

Локальные хуки `.codex/hooks/` и `.claude/hooks/` сохраняются. Новые определения
hooks не считаются доверенными автоматически. `review-reminder.sh` — подсказка,
не доказательство независимого ревью. Разрешения среды могут быть строже
репозитория. Не менять глобальный `core.hooksPath` и не добавлять трейлеры
инструмента в коммиты. Коммиты — небольшие, conventional, по смыслу изменения.
Описание в заголовке и тело каждого нового коммита писать на русском языке.
Стандартные типы и scope Conventional Commits (`feat`, `fix`, `docs`, `api`
и т. п.), имена файлов, идентификаторы и названия технологий сохранять как есть.
Пример: `fix(api): исправить обработку пустого запроса`. Правило действует
для всех агентов и технических сессий проекта; старую историю не переписывать.

## Проверки и доказательства

Команды — существующие цели `Makefile` и CLI из профильных README;
общий запуск описан в `README.md`, эксплуатация — в `deploy/README.md`.
Для изменений Python: `make lint`, `make typecheck`, `make test`; фронта —
`make web-lint`, `make web-typecheck`, `make web-test`, `make web-build`.
Документы — `make docs-check`; хуки — `make hooks-test`.
Для технической итерации обязателен `make audit AUDIT_ARGS="--no-images --strict"`.
При обычной правке документов достаточно относящихся к ней проверок и CI;
исторический DoD SFR-0 не применяется ко всем последующим задачам.
Не выключать проверки и не ослаблять критерии ради зелёного статуса.

Отчёт нужен итерации, эксперименту и измерениям: `docs/reports/`, краткое резюме,
проверяемые результаты, DoD, ограничения, ссылки на ревью и нужные правки
паспорта (лист, ячейка, было → стало, источник). Обычная правка документов
или небольшой фикс не требуют отчётного MD: результат — в документе и его PR,
если он хранится в репозитории.
Значимые решения — дата, решение, причина, альтернативы в `docs/DECISIONS.md`.
Постановка мини-сессии сохраняется в PR, а не отдельным файлом передачи.

Метрики не переписывать вручную: источник — артефакты измерений. Success@k
сравнивать на одинаковых наборах и с одним судьёй; nDCG разных пулов несравним.
Новые оценки `sfr-judge` — `gpt-6-astra/max` согласно
`.codex/agents/sfr-judge.toml`; фактическую модель и effort фиксировать.
Прежние Fable-оценки не переименовывать и не смешивать с новыми.
Пороги принадлежат паре модель × индекс: `ApiSettings`, `meta.json`, `/health`.
Числа, показанные на фронте, получать из API, не хардкодить.

При работе с данными соблюдать действующие контракты и спеки:
OpenAlex — источник MVP; новые источники и eLibrary не добавлять попутно.
Поля API проверять на фактическом ответе; ID вуза получать через resolve.
Сохранять mailto, rate limit ≤10 rps, backoff, дисковый кэш и идемпотентность.
`profile_text` не переводить; пороги эвристик — в settings; отсеянные записи
хранить с флагом, не удалять. Учитывать квоту API перед массовыми запросами.
Замороженные цели и отчёты, исходные данные, метрики, разметку и снимки
воспроизводимости не перезаписывать ради текущей задачи.

## Документы и завершение

Бриф актуализирует продуктовый поток после приёмки общего изменения: отличать
«в ветке», «влито», «выложено» и «проверено пользователями». Уточнения темы
заменяют устаревший текст её основного материала, а не добавляют пересказ в бриф.
Принятое, проверенный факт, гипотеза и история должны быть различимы.
`Closes #N` применим только если полный критерий issue выполнен к merge.
Доска отражает issues, но не принимает решение о готовности.

Паспорт, дек и обоснование — локальные оригиналы в папке документов
`/Users/boris/Desktop/Search for Research`; перед их правкой прочитать её
`AGENTS.md`. CustDev с персональными данными не переносить в git или наружу.
Google Drive обновляет Борис вручную; после локальных правок напомнить ему.

Перед завершением проверить новые документы, дубли, ссылки и оставшиеся
задачи по затронутой работе. Полезное перенести в существующий источник,
свои временные файлы убрать после передачи результата. Не удалять архивы,
доказательства, чужие изменения или данные под видом уборки. `SESSIONS.md`
заморожен; новую хронику раундов в брифе или `brief_history_qa.md` не вести.
