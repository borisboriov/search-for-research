# SFR-1: Мини-тест embedding-моделей на реальных профилях

**Проект:** Search For Research. Контекст итераций: SFR-0 (готово) собрал 261 профиль учёных МФТИ в `data/exports/profiles.jsonl`. Целевая цепочка: база → семантический поиск → сайт.
**Эта итерация (SFR-1):** ответить измерением на главный технический вопрос проекта — *находит ли embedding-поиск релевантных научных руководителей по русскоязычному запросу студента, и какая модель делает это лучше*. Продуктовый порог: у ≥70% запросов хотя бы один релевантный НР в топ-5.
**Режим:** автономный, вопросы задавать некому. Решения — в `docs/DECISIONS.md`. Перед стартом прочитай `docs/REPORT.md` (проблемы данных SFR-0) и `docs/NEXT.md`.

## 1. Скоуп

Делаем: новый пакет `packages/sfr-match` (будущий модуль мэтчинга продукта) с индексацией, поиском и eval-харнессом; golden set запросов; сравнение моделей; чистку текста профилей и замер её эффекта; отчёт с рекомендацией.
НЕ делаем: FastAPI, веб, fine-tune моделей, новые источники данных, RAG-объяснения. Если `profiles.jsonl` отсутствует — пересобери его командами sfr-etl из README (кэш `data/raw/` на месте, сеть почти не понадобится).

## 2. Пакет `sfr-match`

CLI (typer, консольный скрипт `sfr-match`):

1. `sfr-match index --model <name> [--clean]` — прочитать profiles.jsonl → эмбеддинги → FAISS-индекс (+метаданные) в `data/indexes/<model_slug>[_clean]/`. Косинусная близость (нормированные векторы, IndexFlatIP — 261 профиль, ничего сложнее не нужно).
2. `sfr-match search "запрос" --model <name> [-k 10]` — топ-k профилей со score, читабельный вывод в терминал.
3. `sfr-match eval --models a,b,c [--clean/--no-clean] --k 10` — прогнать golden set по всем моделям/вариантам, сохранить ранжирования в `data/eval/runs/`.
4. `sfr-match report` — свести прогоны + судейские оценки в `docs/SFR1_REPORT.md`.

Технические требования: CPU-only (faiss-cpu, sentence-transformers; без GPU-зависимостей); модели скачиваются с HuggingFace при первом запуске — кэшируй стандартно (`~/.cache`), в git не тащить; индексы и eval-артефакты в `data/` (gitignored), но **golden set и судейские оценки — в git** (`packages/sfr-match/eval/` как данные пакета): они — актив проекта.

## 3. Модели для сравнения (4 варианта + бейзлайн)

1. `intfloat/multilingual-e5-base` — основной кандидат. ВАЖНО: E5 требует префиксы `query:` / `passage:` — реализуй per-model препроцессинг, без него результаты будут занижены.
2. `sentence-transformers/paraphrase-multilingual-mpnet-base-v2` — классический мультиязычный бейзлайн.
3. Одна русско-специализированная модель из актуального топа ruMTEB (retrieval) разумного размера (<1.5B параметров) — выбери сам по лидерборду, проверь доступность на HF, зафиксируй выбор в DECISIONS.md.
4. `sentence-transformers/all-MiniLM-L6-v2` — англоязычная модель, выбранная в раннем паспорте проекта. Включаем чтобы ИЗМЕРИТЬ, насколько она проседает на русских запросах (это пойдёт в обоснование смены модели в документах проекта).
5. BM25 (rank-bm25, простая токенизация с лемматизацией не заморачивайся — но lowercase + удаление пунктуации) — лексический бейзлайн: показывает, что даёт семантика сверх «поиска по словам», и задел под будущий гибрид.

Если модель недоступна/не влезает в память — замени аналогом и запиши почему.

## 4. Golden set запросов (30 шт.)

Файл `packages/sfr-match/eval/queries.jsonl`: `{id, text, expect: "in-domain"|"edge"|"out-of-domain", comment}`.

Требования к составу — запросы должны выглядеть как реальный ввод студента (разговорные, 1–2 предложения, НЕ списки ключевых слов), распределение — под фактические темы корпуса (см. топ-15 тем в REPORT.md: физика частиц, сверхпроводимость, квантовый транспорт, полупроводники, нейтрино, лазеры/плазма — плюс имеющиеся NLP, оптимизация, эконом-моделирование, нейроинтерфейсы):

- 22 in-domain, среди них обязательно: ~6 на русском разговорном («хочу заниматься машинным обучением для анализа текстов, интересна тема депрессии в соцсетях»), ~4 с англицизмами вперемешку («интересен deep learning для физики частиц»), ~4 кросс-языковых по смыслу (русский запрос ↔ англоязычные профили: «оптимизация маршрутов доставки» → Vehicle Routing), ~4 узких («поиск тёмной материи», «мемристоры и нейроморфные вычисления»), ~4 широких («что-нибудь на стыке физики и программирования»).
- 4 edge: очень короткие («квантовые компьютеры»), с опечатками, тема есть но на периферии корпуса.
- 4 out-of-domain (история, юриспруденция, кулинария, маркетинг) — проверка поведения «хорошего ответа нет»: фиксируем, какие score выдаёт каждая модель, и есть ли отсечка, при которой можно честно сказать «мы никого не нашли» (это будущий порог продукта).

Стартовые примеры формулировок (расширь до 30 сам, в том же стиле): «Пишу диплом про нейросети для медицинских изображений, ищу научрука», «Интересна физика элементарных частиц, эксперименты на коллайдере», «Хочу в тему сверхпроводимости, но боюсь что слишком сложно», «Занимался олимпиадным программированием, хочу применить алгоритмы к чему-то научному», «Интересуют графовые нейросети и обработка естественного языка», «Экономическое моделирование, теория игр».

## 5. Методика оценки

**Судейство (LLM-as-judge — судишь ты сам, это твоя сильная сторона):**

1. Пулинг: для каждого запроса собери объединение топ-5 всех моделей/вариантов → уникальные пары (query, author).
2. Каждую пару оцени по рубрике, глядя на ПОЛНЫЙ profile_text (не только темы): **2** — прямое совпадение специализации, студенту стоит писать этому НР; **1** — смежная область, осмысленный запасной вариант; **0** — нерелевантно. Оценивай пару в отдельности, НЕ зная, какая модель её выдала (сортируй пул по author_id, не по score).
3. Оценки — в `packages/sfr-match/eval/judgments.jsonl`: `{query_id, author_id, grade, rationale}` (rationale — одна строка). Кэшируй: пара оценивается один раз, оценка переиспользуется всеми моделями.
4. Отдельным файлом `eval/judgments_for_review.md` выведи 20 случайных пар (запрос + имя + темы + оценка + rationale) — для утренней ручной проверки человеком.

**Метрики (посчитай по judgments для каждой модели/варианта):**

- **Success@5** (главная, продуктовая): доля in-domain запросов, где в топ-5 есть grade=2. Порог проекта: ≥70%.
- Success@5 при grade≥1 (мягкая), nDCG@10 (grade как gain), MRR по первому grade=2.
- Для out-of-domain: средний top-1 score модели и число «ложных находок» (grade≥1 быть не должно по построению — если вдруг есть, отметь).
- Время индексации и средняя латентность поиска (CPU).

**Эксперимент с чисткой текста** (проблемы №1–2 из REPORT.md): реализуй в sfr-match препроцессор профиля — удаление LaTeX/MathML-мусора (`\ensuremath`, `$…$`, `\text` и пр.) и выбрасывание «аннотаций-списков авторов» (эвристика: высокая доля паттернов «Фамилия, И.;»). Прогони ЛУЧШУЮ по Success@5 модель в вариантах clean/no-clean и сравни. Чистку реализуй как функцию над profile_text при индексации (сырой jsonl не переписывай).

## 6. Тесты

Юнит-тесты на чистую логику: LaTeX-чистка (несколько реальных примеров из данных), детектор «аннотаций-списков авторов», расчёт nDCG/MRR/Success@k на маленьком синтетическом фикстур-наборе (сверь nDCG с ручным расчётом), препроцессинг E5-префиксов, загрузка/валидация queries.jsonl и judgments.jsonl (схема, уникальность id). Сами модели в юнит-тестах не гонять (долго) — для эмбеддера сделай фейк-протокол. Один smoke-тест с реальной маленькой моделью пометь `@pytest.mark.slow`, из CI исключи. Coverage-порог репозитория держи.

## 7. Отчёт и Definition of Done

- Сводная таблица: модель/вариант × (Success@5 строгая и мягкая, nDCG@10, MRR, латентность, размер модели).
- **Рекомендация: какую модель берём в SFR-2 и почему**; дал ли эффект clean; что показал BM25 (нужен ли гибрид); какой порог score использовать для «никого не нашли» (по out-of-domain).
