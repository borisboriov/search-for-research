## 1. Скоуп

Делаем: FastAPI-сервис `/match` в `apps/api/`; возврат FAISS на путь поиска (Linux); контейнеризация + замер ресурсов; расширение OOD-набора и перекалибровка порога; эксперимент с составом profile_text; заготовка внешнего тест-сета.
НЕ делаем: фронтенд (SFR-3; Борис параллельно ведёт дизайн-ресерч — интерфейсных решений не предвосхищать), авторизацию, PostgreSQL/pgvector, RAG-объяснения, дедупликацию авторов, новые вузы.

## 2. FastAPI `/match` (`apps/api/`, пакет в workspace)

По NEXT.md §1, плюс уточнения:

- `POST /api/match {query: str (3..500), k: int = 10}` → `{results: [...], below_threshold: bool, index_version: str}`. В result — полная открытая карточка: author_id, name, institution, h_index, works_count, topics, score (0..1), profile_text. Продуктовое решение (план MVP v1.3): **карточки НР открытые и бесплатные** — API отдаёт их без авторизации; монетизация будет на сервисах, не на данных.
- `GET /api/supervisors/{author_id}` — карточка по id (для будущих открытых страниц фронта).
- `GET /api/health` → `{status, model, index_version, profiles_count}` (version из meta.json индекса).
- Загрузка модели и индекса — один раз в lifespan + warmup; переиспользовать `sfr_match.search.load_backend`; индекс собирается офлайн (`make index`), API его не строит.
- Валидация и ошибки: пустой/слишком длинный запрос → 422 с человекочитаемым detail; индекс не найден → понятный fail при старте, не 500 на первом запросе.
- CORS: разрешить localhost-происхождения (для будущего фронта), конфигурируемо через settings.
- Тесты: TestClient с фейковым backend-протоколом (модель в юнит-тестах не грузить); контракт ответа; below_threshold-логика; health. Один smoke с реальной моделью — `@pytest.mark.slow`.

## 3. FAISS и контейнер

- Dockerfile для API (python slim, uv, CPU-only torch; модель НЕ печь в образ — скачивание в volume/кэш при первом старте). docker-compose.yml для локального запуска.
- В Linux-контейнере вернуть FAISS на путь поиска; тестом `test_numpy_scan_matches_faiss_exactly` подтвердить идентичность выдачи. На macOS остаётся NumPy-скан — выбор бэкенда автоматический, зафиксировать в DECISIONS.md.
- **Замер ресурсов в контейнере (для выбора VPS — пойдёт в отчёт и в план):** RAM после старта и под нагрузкой, время холодного старта, латентность p50/p95 при 1 и 4 конкурентных запросах, размер образа. Тот же замер для запасной mpnet (переключение моделью через settings — должно работать из коробки). Если docker на машине недоступен — замерить в venv и честно пометить ограничение.

## 4. Порог отсечки и OOD (долг SFR-1)

- Расширить OOD до ≥15 честных посторонних запросов. Урок SFR-1: сначала ПРОВЕРЬ поиском по корпусу, что запрос действительно постороний (истории с хлебцами не повторять) — кандидат включается в OOD только если вручную подтверждено отсутствие релевантных профилей; процедуру опиши в отчёте.
- Перекалибровать порог (сейчас 0.35 по top-1) на новых точках; критерий: 0 ложных отсечек in-domain при максимальном покрытии OOD. Порог — в settings, отдаётся через health.
- Если порог изменится — это продуктовая цифра: подготовить файл `../SFR_правка_порог_отсечки_<дата>.md` по правилам родительского CLAUDE.md (сам `01_core` не трогать).

## 5. Эксперимент: состав profile_text

Гипотеза из SFR-1: основной сигнал — в строке ключевых тем. Прогнать FRIDA (и mpnet как контроль) на вариантах индекса: (а) только темы; (б) темы + названия работ; (в) полный profile_text (бейзлайн). Метрики: Success@5, Success@1 по существующим judgments (новые пары — судить по рубрике SFR-1, кэшировать в judgments.jsonl). Вывод в отчёт: что кладём в индекс дальше и почему; это же определит, что важно показывать на карточке.

## 6. Внешний тест-сет (заготовка)

Формат `packages/sfr-match/eval/external_queries.jsonl` (та же схема, что queries.jsonl, + поле source: "student"), CLI `sfr-match eval --queries external` и README-инструкция для Бориса/Светы: как собрать 10–15 запросов реальных студентов (не показывая корпус) и куда положить. Сами запросы соберут люди — файл оставить пустым, не выдумывать.
