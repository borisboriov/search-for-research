# apps/api — сервис поиска научных руководителей

FastAPI поверх индекса, собранного офлайн (`make index-sfr5`). Модель и индекс
грузятся один раз при старте, прогреваются и переиспользуются; API индекс **не строит**.

## Эндпоинты

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/api/match` | `{"query": "…", "k": 10}` → карточки НР, `below_threshold`, `index_version` |
| `GET` | `/api/supervisors/{author_id}` | одна карточка по OpenAlex-id |
| `GET` | `/api/health` | модель, версия индекса, число профилей, порог, бэкенд поиска |

Карточки **открытые и бесплатные** — авторизации нет по продуктовому решению
(план MVP v1.3): монетизация будет на сервисах вокруг данных, не на данных.

`below_threshold` — предупреждение «уверенных совпадений нет», а не отказ:
выдача возвращается всегда (SFR-1 показал перекрытие распределений score).

## Запуск

```bash
make index-sfr5                 # собрать индекс (офлайн, один раз)
make api                        # uvicorn на localhost:8000
curl -s localhost:8000/api/health | jq
curl -s localhost:8000/api/match -H 'content-type: application/json' \
  -d '{"query":"нейросети для медицинских изображений","k":5}' | jq
```

В контейнере: `make docker-up` (см. `docker-compose.yml` в корне репозитория).

## Настройки

Переменные окружения с префиксом `SFR_API_` (см. `settings.py`):
`SFR_API_MODEL`, `SFR_API_INDEX_ROOT`, `SFR_API_INDEX_DIR`, `SFR_API_COMPOSE`,
`SFR_API_SCORE_THRESHOLD`, `SFR_API_CORS_ORIGINS`, `SFR_API_MAX_K`.
Переключение на запасную модель — `SFR_API_MODEL=mpnet` плюс собранный под неё индекс.

## Аналитика текущего PoC

Аналитика хранится отдельно от каталога/ETL: PostgreSQL через SQLAlchemy 2 и
Psycopg 3, отдельный Alembic version table `analytics_alembic_version`.
Текущая цепочка миграций: `analytics_0001` (таблицы), `analytics_0002`
(повторная доставка по visit/sequence), `analytics_0003` (HTTP приёмника).

API включает сбор при непустой `SFR_API_ANALYTICS_DATABASE_URL`. Runtime-роль
имеет INSERT и SELECT только идентификаторов, необходимых для `RETURNING`;
права UPDATE, DELETE, DDL и чтение полных запросов ей не выдаются. Оператор и
read-only исследователь подключаются отдельно. Миграции запускает оператор:

```bash
SFR_ANALYTICS_MIGRATION_DATABASE_URL=postgresql+psycopg://... \
  uv run python -m sfr_api.analytics.migrate \
  --runtime-role sfr_runtime --reader-role sfr_reader
```

Соединения ограничены: pool 2, overflow 0, ожидание пула/подключения 1 секунда,
statement timeout 1 секунда, lock timeout 500 мс. Смена сервера БД требует
изменения подключения; каталог, файловый индекс и модель остаются на месте.

Каждая принятая порция сначала попадает в fsynced JSON-файл (0600) в
`SFR_API_ANALYTICS_SPOOL_DIR` (каталоги 0700, постоянный том `/analytics`).
Поиск ожидает журнал не более 250 мс, приёмник — 500 мс.
В процессе одновременно допускаются две физические операции append; слот
освобождается после фактического завершения, даже если HTTP ожидание истекло.
writer_busy быстро отказывает новым записям (приёмник 503, поиск fail-open);
append_rejected — счётчик процесса и безопасная log-категория, не постоянный
счётчик между рестартами. При таймауте
приёмник отвечает 503; фоновая запись ещё может завершиться, поэтому клиент
повторяет те же event_id/sequence. Сбой сбора не изменяет ответ поиска, но
виден в диагностическом сообщении и счётчике сбоев процесса. При неисправном
диске абсолютная полнота поисковых фактов не гарантируется.

Фоновая догрузка стартует с API и повторяется каждые 5 секунд. Одна транзакция
записывает порцию с `ON CONFLICT DO NOTHING`; event_id и (visit_id, client_seq)
устраняют повторные доставки, search_id/request_id отделяют попытки. Первый
принятый факт сохраняется при конфликте идентификаторов. После commit файл
сохраняется в gzip-архиве; pending удаляется только после fsync архивной копии.
Рестарт между этими операциями повторяет транзакцию безопасно. История не
удаляется по возрасту. Повреждённые записи и незавершённые временные файлы
старше минуты переходят в quarantine с сохранением байтов.

Буфер ограничен 512 МиБ pending и 10 000 файлов; резерв свободного диска —
64 МиБ. Это аварийная граница отказа записи, а не достаточный эксплуатационный
запас. Архивы продолжают занимать диск; диагностика показывает объём каждого
каталога, свободное место, возраст очереди, последнюю успешную догрузку и
категории сбоев. При недостатке места оператор делает внешнюю проверенную
выгрузку и расширяет место; автоматического удаления истории нет.

`analytics_searches` хранит серверное время, статус, результат, модель/индекс,
версию приложения, пороги, параметры, cache hit, задержки и упорядоченный список
ID/score/rank/grade. `analytics_context` хранит полный исходный запрос и отдельно
строку, переданную поиску после strip. Текст не размножается по событиям.
Старый успешный JSONL `/match` остаётся совместимым; постоянный экспорт
восстанавливает его query из закрытого контекста, остальные поля — из legacy
метаданных. Ошибки являются отдельными фактами, не confidence none.

`analytics_events` хранит клиентское событие; `analytics_event_context` —
допустимый закрытый контекст и ingest_request_id. Event.request_id обозначает
связанный запрос поиска; ingest_request_id — фактический HTTP приёмника.
Серверные received_at/completed_at/persisted_at и клиентский client_at —
`timestamptz`; соединения работают в UTC. Порядок UI анализируется по client_seq
внутри визита, а период — по received_at. Неверные клиентские часы не меняют
фильтрацию периода; client_at остаётся диагностическим наблюдением. Монотонные
часы измеряют длительность поиска, не календарную разницу серверов.

`POST /api/events` — внутренний маршрут за Next handler: максимум 10 событий,
16 КиБ до JSON-разбора. `{accepted: [event_id, ...]}` означает устойчивую
запись на диск; при недоступном журнале ложного подтверждения нет. Контракт v1
и перечисления находятся в `analytics/contracts.py`: неизвестные поля и текст
запроса в событии отвергаются. Успех clipboard имеет отдельное событие от
ошибки. SSR/prefetch не создают просмотры, API не выводит их из сетевых запросов.

Закрытый контекст допускает только raw IP, URL/Referer без credentials, query
parameters и fragment, User-Agent и Accept-Language (по 512 символов).
Authorization/Cookie/Set-Cookie/X-Revalidate-Secret и любые остальные заголовки
не собираются. X-SFR-Client-IP принимается только от API peer, попадающего в
`SFR_API_ANALYTICS_TRUSTED_PROXY_CIDRS`; Caddy перезаписывает его, Next передаёт
по проверенной внутренней цепочке. Произвольный X-Forwarded-For не является
источником идентичности. Пользовательские имена и контакты в запросе остаются:
это чувствительные исследовательские данные, а не обезличенные логи.

Сервер помечает SFR-Rehearsal/SFR-Technical User-Agent как declared_technical,
а bot/crawler/spider как suspected_bot. Это заявленные/предполагаемые категории,
не проверенная идентификация человека. Cookie и аккаунты не используются;
visit_id — наблюдаемый визит вкладки по sessionStorage, не уникальный человек.
Закрытие браузера или потеря сети могут оставить неполную последовательность.

Интеграционные проверки используют настоящий PostgreSQL:

```bash
SFR_TEST_ANALYTICS_DATABASE_URL=postgresql+psycopg://... \
  SFR_REQUIRE_ANALYTICS_PG=1 uv run pytest apps/api/tests/test_analytics_pg.py --no-cov
```

Тестовая БД должна быть отдельной; тесты создают синтетические записи и
изолированные NOLOGIN роли для проверки прав. Они не заменяют репетицию Compose,
backup/restore и измерения с реальной FRIDA. Команды оператора, backup и
выгрузка описаны в [deploy/README.md](../../deploy/README.md).
