# SFR-4b: Статический анализ и аудит зависимостей в CI (мини-итерация, ~1–2 часа)

**Контекст:** после SFR-4 код отрепетирован в боевой компоновке, независимое LLM-ревью проведено. Добавляем автоматический слой, который ловит то, что LLM пропускает: уязвимые зависимости, известные небезопасные паттерны, секреты в коммитах, проблемы Docker-образов. **Ограничения:** репозиторий приватный, **никаких платных возможностей GitHub** (CodeQL/Advanced Security исключены), никаких SaaS-аккаунтов — только открытые инструменты, работающие офлайн в CI и локально. Прочитай `docs/REVIEW_SFR3.md` и `docs/SFR4_REPORT.md` (что уже закрыто), `.github/workflows/ci.yml`, `Makefile`.
**Режим:** автономный, решения — в `docs/DECISIONS.md`. Код продукта менять только для исправления реальных находок.

## 1. Инструменты (все бесплатные, версии запинить)

| Слой | Инструмент | Что |
|---|---|---|
| Зависимости Python | `pip-audit` (по `uv.lock`/экспорту requirements) | известные CVE |
| Зависимости Node | `npm audit --audit-level=high` в `apps/web` | известные CVE |
| Код Python | `bandit -r packages apps/api -ll` | небезопасные паттерны (subprocess, yaml.load, hardcoded creds…) |
| Код Python+TS | `semgrep scan --config p/python --config p/typescript --config p/nextjs --config p/secrets --config p/docker --metrics=off` (офлайн, без аккаунта; правила кэшировать/зафиксировать версии) | паттерны безопасности и качества |
| Секреты | `gitleaks detect --source . --redact` (+ `--log-opts` по всей истории один раз в отчёт) | ключи/токены в коде и истории |
| Образы и файловая система | `trivy fs --severity HIGH,CRITICAL .` и `trivy image` для собранных `sfr-api`, `sfr-web` (в CI — только `fs`, если сборка образов слишком долгая; обосновать) | CVE в зависимостях и базовых образах |
| Dockerfile | `hadolint apps/api/Dockerfile apps/web/Dockerfile` | лучшие практики |

## 2. Интеграция

- `make audit` — запускает всё локально одной командой (инструменты ставятся в dev-зависимости uv / npx, без глобальных установок; чего нет в PATH — понятное сообщение, а не падение).
- CI: отдельный job `security` в `.github/workflows/ci.yml` (или `security.yml`): на push/PR + **еженедельный cron** (новые CVE появляются без изменений кода). Политика: **High/Critical — падение job**; Medium/Low — предупреждение в логе, не падение. Уязвимости без доступного фикса и ложные срабатывания — только через явный allowlist с обоснованием и датой пересмотра (`.semgrepignore`, `pip-audit --ignore-vuln`, `.trivyignore`, `.gitleaks.toml`), никаких «выключить правило целиком».
- pre-commit: добавить `gitleaks` (быстрый, ловит секреты до коммита); тяжёлые сканеры в pre-commit не ставить.
- Ничего из этого не должно требовать секретов или токенов в GitHub.

## 3. Первый прогон — базовая линия

Запусти всё локально на текущем main и **исправь реальные находки** (обновить зависимость, поправить код); ложные — в allowlist с обоснованием. Отдельно: `gitleaks` по всей истории git — если в истории есть секрет, не переписывать историю сам: записать в TODO_BORIS с инструкцией (ротация ключа важнее чистки истории).

## 4. Definition of Done

`docs/SECURITY_CI.md`: что и как проверяется, где allowlist и как в него попадать, как читать красный job; таблица базовой линии: инструмент → найдено → исправлено / в allowlist (с причиной) → осталось. Чеклист:

- [ ] `make audit` зелёный локально на текущем main (с allowlist только обоснованных пунктов)
- [ ] CI job `security` добавлен, версии инструментов запинены, cron еженедельный; **после пуша Бориса** job должен пройти — если требует токенов/платных фич, это дефект спеки
- [ ] `gitleaks` в pre-commit; история проверена, результат в отчёте
- [ ] Реальные находки исправлены с тестами (если затронут код); `make lint/typecheck/test`, `make web-*`, `make eval` (≡ SFR-2) — зелёные
- [ ] `docs/SECURITY_CI.md`; DECISIONS/SESSIONS/TODO_BORIS обновлены; в `.claude/agents/sfr-reviewer.md` (если файл есть) — строка чеклиста «`make audit` зелёный» (файл вне git, править локально)

Не дотянул — опиши честно, не маскируй.
