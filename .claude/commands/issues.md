Ты работаешь с задачами проекта Search For Research: issues репозитория
`borisboriov/search-for-research` и доска «SFR — задачи»
(https://github.com/users/borisboriov/projects/5, owner `borisboriov`, номер 5).

**Правила таксономии — в `CLAUDE.md`, раздел «Задачи — в GitHub Issues».** Это мастер,
здесь их копии нет: перечитай раздел перед работой, если не держишь в контексте. Здесь —
процедуры: что делать руками в каком порядке.

**Инструмент — `gh`, не MCP-коннектор:** через коннектор поля проектов не пишутся.
Нужен scope `project` (`gh auth refresh -s project`).

**Границы (нарушение = переделка).** Не меняй milestones, не трогай лейблы `sveta` и
`decision`, не удаляй issues — ни закрытые, ни открытые: внешнему агенту нужна история.
Всё это — территория Бориса. Если задача требует такого изменения, скажи об этом словами
и предложи, а не делай.

Запрос: **$ARGUMENTS**. Определи по нему сценарий; если он не подходит ни под один —
действуй по смыслу, опираясь на правила ниже. Если запрос пустой — покажи дайджест.

## Сценарий «завести задачу»

Триггер: описание работы, «заведи issue», «новая».

1. **Сначала поиск дублей** — `gh issue list --search "<2–3 ключевых слова>" --state all`.
   Нашёл похожее — не заводи второе: покажи найденное и спроси, дополнить комментарием
   или всё-таки завести отдельное.
2. **Лейблы: ровно один «кто» + одна-две «области» + приоритет.** Если из описания
   непонятно, кто делает или насколько срочно, — спроси, а не угадывай. Приоритет без
   лейбла `P0`–`P2` не виден через API issues, поэтому он обязателен.
3. **Milestone — не ставь сам** (это правило границ). Предложи подходящую веху словами.
4. **Тело issue** — по структуре, принятой в репозитории: «Что сделать» (действие и
   критерий), «Откуда» (что породило задачу, с цитатой), «Контекст» (оценка времени,
   подводные камни), «Критерий готовности».
5. **Ссылки** — на файлы репозитория через `blob/main` без номера строки, параграф
   называй словами. Permalink по SHA — только если важна конкретная строка конкретной
   версии. Удалённые файлы не ссылать: имя текстом плюс дословная цитата.
6. **После создания** — `make board-sync`, чтобы issue попал на доску с полями.
   Покажи номер и ссылку.

## Сценарий «триаж и гигиена»

Триггер: «триаж», «гигиена», «разбери задачи», после большого треда.

1. `make issues-audit` — механические проверки: ошибки таксономии, открытые `agent`
   без milestone, залежавшееся, кандидаты в дубли, чего нет на доске.
2. Разбери вывод: **ошибки** таксономии чини сам (`gh issue edit N --add-label …`) —
   кроме случаев, где нужно решить, чья задача или какой приоритет: это к Борису.
   **«Поводы посмотреть»** — не чини молча, вынеси списком с рекомендацией по каждому.
3. Кандидатов в дубли проверь чтением обоих issue, а не по заголовку: скрипт считает
   пересечение слов и ошибается.
4. `make board-sync` в конце.
5. Итог — короткая сводка: что починил, что требует решения Бориса.

## Сценарий «дайджест»

Триггер: «дайджест», «что на мне», «что горит», пустой запрос.

1. `gh issue list --label human --state open --json number,title,labels,milestone` —
   что на Борисе; отдельно `--label decision` — что ждёт решения.
2. Сгруппируй по приоритету (`P0` → `P1` → `P2`), внутри — по milestone.
3. Отдельной строкой — ближайшая веха и сколько до неё дней; задачи с датой в заголовке
   (дедлайны подач, конкурсы) вынеси наверх независимо от приоритета.
4. Отдельно — `--label blocked`: чего ждём и не отпало ли ожидание.
5. Вывод — компактная таблица, а не простыня. Три-пять строк «что делать первым».

## Сценарий «закрыть итерацию»

Триггер: «закрыть SFR-N», «итерация сделана».

1. `gh issue list --label agent --milestone "<веха>" --state all` — что заказывалось.
2. Для каждого открытого: проверь `git log --grep "Closes #N"` — не закрыт ли он на самом
   деле коммитом. **Вручную issue без коммита не закрывать** — это правило репозитория.
3. Незакрытое раздели на «переезжает в следующую итерацию» и «отпало»; по каждому —
   рекомендация, решение за Борисом.
4. Находки ревью итерации — issues с лейблом `from-review` (плюс `agent` + область).
5. `make board-sync`; если открылась новая итерация — поменяй `CURRENT_ITERATION_PREFIX`
   в `scripts/gh_board_sync.py` и скажи об этом в сводке.

## Полезные команды

```bash
make issues-audit          # гигиена: лейблы, дубли, залежавшееся
make board-sync-dry        # план синхронизации полей доски
make board-sync            # применить
gh issue list --label human --state open
gh issue list --search "дедуп" --state all
gh issue create --title "…" --label "agent,code,P2" --body-file -
gh issue edit 42 --add-label "P1" --remove-label "P2"
gh issue comment 42 --body "…"
```

В конце любого сценария, который создавал или правил issues, прогони `make board-sync`
и скажи одной строкой, что изменилось на доске.
