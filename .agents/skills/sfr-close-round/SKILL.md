# Завершение работы SFR

«Подготовить/закрыть раунд» не означает разрешения на merge, main, деплой,
загрузку Drive или запуск следующей сессии. Мастер состояния —
`docs/product/brief.md`; DECISIONS хранит решения и основания. Обычные правки
документов завершаются результатом и PR, без отдельного отчёта.

## Подготовить до merge

1. Получи результат `$sfr-verify-session`: принятые критерии, ограничения,
   незакрытые задачи. Если нужен дополнительный факт, проверь его; не объявляй
   работу законченной по одному сообщению технического автора.
2. Перед изменениями общей ветки согласуй передачу и убедись, что технический
   автор прекратил запись. Координация другого чата требует разрешения Бориса;
   при его отсутствии не посылай сообщения туда. Используй ту же рабочую
   ветку/PR, не пиши в main и не переключай чужой checkout во время работы.
3. Продуктовый поток обновляет затронутые `docs/product/`: бриф, спеку MVP,
   обоснованные ссылки и формулировки. Бриф отражает факты **на момент записи**:
   «готово в PR» не заменять на «влито/выложено». В DECISIONS добавь только
   существенные новые решения, без второго блока состояния и хроники действий.
4. Для изменений принятых утверждений паспорта проверь предложения по ячейкам,
   источники и оговорки. Локальные бинарники правит продуктовый поток в рамках
   поручения, прежние версии сохраняются в архиве. Согласуй затронутые паспорт,
   питч, обоснование и бриф. Борис загружает обновление Drive сам; до его
   подтверждения соответствующая issue остаётся открытой.
5. Проверь связанные issues по `$issues`. Мгновенно исправленные замечания
   остаются в истории PR; отдельные задачи нужны для самостоятельных хвостов.
   Для неполного DoD используй обычную связь с PR, не `Closes`. Не закрывай
   задачи из-за наличия закрывающего слова в коммите.
6. Получи от технического исполнителя в существующем PR перечень его основной
   и служебных веток/worktree: точные имена, пути, SHA и состояние записи;
   где лежат результаты, выгрузки, резервные копии и доказательства, включая
   ignored/untracked. Это пакет для очистки после merge, а не новый отчёт.
   Исполнитель готовит перечень и сохранность результатов; продуктовый поток
   проверяет выполнение очистки. При отсутствии временных веток/worktree
   достаточно явно указать это. Готовность к merge и завершение всего раунда
   остаются разными состояниями.
7. Закоммить продуктовые изменения в согласованную ветку и пройди относящиеся
   к ним проверки, включая `make docs-check` и `git diff --check`. Любые новые
   коммиты требуют проверки затронутого diff и свежего подтверждения ревью;
   CI должен быть зелёным на актуальной версии PR. Финальное подтверждение
   SHA — комментарий PR, а не следующий коммит отчёта; после него выполни
   `make handoff-check PR=N`. Добавь итог `sfr-product-review` по формату
   `$sfr-verify-session` на окончательные base/head; `ready` допустим только
   после успешной проверки. Не дублируй уже записанный итог той же версии.
   Передай Борису результат,
   оставшиеся действия и ссылку на PR. На этом подготовка может быть завершена.

## После фактического merge

1. Проверь, какая принятая версия фактически вошла в merge, её ревью и CI.
   Закрой только issues с выполненным полным DoD: незавершённые выкладка,
   пользовательская проверка или Drive сохраняют соответствующую задачу открытой.
   Сверь доску по `$issues`; успешную автоматическую синхронизацию не дублируй.
   Подтверждение фактического завершения сохрани в существующем PR/issue.
2. Сверь перечень очистки с текущими Git refs и worktree. Проверь tracked,
   untracked и ignored файлы, незакоммиченные изменения и использование папок
   работающими сессиями. Установи принадлежность каждого worktree; чужая или
   продолжающаяся работа не входит в очистку завершённой сессии.
   Основной checkout и его пользовательские изменения сохрани.
3. Перенеси нужные результаты в постоянные источники. Выгрузки, backup и
   доказательства вне git сохраняй в закрытом локальном архиве с проверкой
   контрольных сумм. Воспроизводимые зависимости и кэши архивировать не нужно.
   Проверяй не только `--merged`: после squash/cherry-pick разные SHA могут
   содержать уже включённые правки. Уникальная работа требует сохранения или
   решения Бориса, а не повторного merge. Если сохраняешь отдельную историю
   через Git bundle, проверь его восстановление до удаления исходных refs.
   Для полностью влитой истории отдельная копия не обязательна.
4. Включи в пакет закрытия точный список удаляемых локальных/удалённых веток
   и освобождаемых worktree, состояние сохранённых данных и оставшиеся действия.
   Merge сам по себе не разрешает delete/force. Если Борис уже согласовал этот
   пакет, выполни его без повторного вопроса; иначе запроси одно согласование
   конкретного пакета. Ожидание решения явно остаётся незавершённым пунктом раунда.
5. После согласования освободи завершённые worktree и удали только перечисленные
   ветки. Для worktree, управляемого приложением, используй штатное архивирование;
   ignored данные предварительно сохраняй отдельно. Для обычных Git worktree
   используй адресное удаление после проверки сохранности. Перед удалением refs
   повторно сверяй SHA; удалённые refs защищай проверкой ожидаемой версии.
   Не завершай работающий CLI и не останавливай контейнеры/тома ради очистки
   веток. Общий `git clean`, удаление архивов, доказательств и чужих файлов
   в эту процедуру не входят.
6. Проверь результат: выполненные issues закрыты, доска согласована, удалённые
   refs/worktree отсутствуют, архивы читаются и их контрольные суммы совпадают,
   основной checkout и чужие изменения сохранены. Итог в существующем PR
   содержит фактические SHA merge/принятой версии, что очищено и где сохранено,
   что ещё не сделано и кто продолжает. При незавершённой очистке не объявляй
   весь раунд закрытым; укажи конкретный остаток.

Если после подготовки документов появились новые факты для брифа, внеси их
допустимым путём — в рабочей ветке с PR, не прямой записью в main; второй PR
только ради пересказа факта merge не нужен. Деплой, проверка пользователями
и обновление Drive остаются отдельными незавершёнными действиями до подтверждения.

Перенеси результаты из собственных временных материалов в PR/issues или
отчёт эксперимента, затем удали только эти временные материалы. Закрытие
PR не доказывает, что локальные изменения сохранены. Итог в чате: что принято
и реально завершено, ссылки, что осталось и кто делает следующий шаг.
