# Независимое ревью SFR

Используй отдельного субагента `sfr-reviewer`: нативная роль —
`.codex/agents/sfr-reviewer.toml`, роль Claude — `.claude/agents/sfr-reviewer.md`.
Если именованная роль недоступна, дай её инструкции отдельному агенту и
обозначь это в результате. Не подменяй независимое ревью самопроверкой автора.

Для порученной ревизии без PR зафиксируй файлы/версии и вопросы; верни находки
в чат. Не создавай PR, отчёт или цикл исправлений ради проверки. Для изменённого
PR действуют все этапы ниже; обычное обсуждение их не запускает.

## Проверяемая версия

Зафиксируй конкретные `base_sha` и `head_sha`, постановку и PR. Не выдавай
незакоммиченные правки за часть проверенной версии. Ревьюер читает файлы
именно на заданном SHA, а не изменяемые файлы общего checkout. База — текущая вершина целевой ветки на GitHub, полученная через Git refs API;
поле PR `baseRefOid` может отставать и для этого недостаточно. Если целевая ветка
продвинулась, проверь актуальный диапазон, обнови подтверждение и CI.

Первому ревьюеру передай чистый контекст: задачу, критерии, base/head, пути
доказательств и необходимые проектные правила. Не передавай переписку автора,
его предполагаемые дефекты или желаемый вердикт. Для эксперимента/техитерации
добавь спеку и отчёт; для обычной docs-правки — документ и постановку из PR/issue.
Отсутствующий отчёт или спеку не создавай только ради ревью. Для документов
проверь источники, статус утверждений, сохранность оснований и ссылки;
требования к содержанию не заменяются отсутствием ошибок Markdown.

Ревьюер не меняет исходники и конфигурацию. Его результат: проверенный
диапазон, подтверждённые находки с местом и последствием, severity, ограничения
проверки и вердикт. Critical/High подтверждаются цитатой; предположение,
которому нужен запуск, помечается как непроверенное. Результат может вернуться
сообщением; временный файл нужен только при реальной необходимости.

## Исправления и финальное подтверждение

Автор исправляет подтверждённые замечания в пределах поручения и запускает
подходящие проверки. Ревьюер проверяет исправления, затронутый контекст и diff
от предыдущей проверенной вершины до новой. Для повторной проверки передай
прежние находки и новый диапазон; при изменении скоупа нужен полный проход.
Любой последующий коммит делает прежнее подтверждение неактуальным.

Продолжай цикл исправление → проверки → независимая перепроверка, пока
критерии выполнены. Неподтверждённая гипотеза не становится обязательным фиксом.
При повторении той же проблемы без прогресса, противоречивых требованиях или
необходимом решении вне поручения верни конкретный блокер; не расширяй скоуп
и не объявляй успех. Обоснованно отложенные хвосты должны быть видимы.

Немедленно исправленные находки зафиксируй в PR без отдельной issue.
Самостоятельный оставшийся хвост — issue `from-review` по `$issues`, после
поиска дублей. Для техитерации/эксперимента краткий итог включи в её отчёт;
обычная docs-правка отдельного отчёта не требует. Закоммить все необходимые
изменения, включая отчёт, **до последнего подтверждения**.

Финальное подтверждение помести новым комментарием в PR: что проверено,
открытые находки/ссылки, вердикт и ровно один машинный маркер:

```text
<!-- sfr-review {"base":"<полный base SHA>","head":"<полный head SHA>","reviewer":"sfr-reviewer","verdict":"pass","blocking_findings":0} -->
```

Подставь фактические SHA из 40 hex-символов; `pass` и ноль блокеров — только
по результату независимого ревью. Для отказа публикуй новый маркер с
`verdict: fail` и фактическим числом блокеров; не редактируй старое подтверждение.
Последний комментарий с маркером отменяет прежний, включая отказ или устаревший
SHA. Затем выполни `make handoff-check PR=N` с номером PR: цель читает GitHub,
требует OPEN, актуальные base/head и успешные checks/web/audit. Она также сверяет фактический checkout каждого CI job с merge актуальных
base/head и повторно читает PR после проверки. Записанное подтверждение не
доказывает качество/независимость ревью; защиту ветки команда не настраивает. Сверь обязательные CI с актуальной версией PR
(учитывая синтетический merge-коммит, если workflow проверяет его). Pending,
missing, failed, skipped или cancelled не объявляй зелёным CI. Ревью и CI —
разные доказательства; рекомендация принять не разрешает merge.

Раздел с названием «ревью», старый REVIEW-файл и Stop-напоминание не являются
подтверждением актуальной версии. Удали только собственный временный файл
после переноса результата; чистку репозитория и удаление веток не выполняй.
