# Issues и передача работы SFR

Репозиторий — `borisboriov/search-for-research`; доска —
https://github.com/users/borisboriov/projects/5. Задачи и их статусы живут
в issues, результаты и ревью реализации — в PR. Этот skill — мастер
таксономии; `AGENTS.md` задаёт общие границы действий.

## Таксономия и границы

У каждой issue ровно один лейбл «кто», одна-две области и один приоритет:

| Кто | Значение |
|---|---|
| `agent` | работа технической сессии в пределах постановки |
| `human` | руки или решение Бориса |
| `sveta` | задача Светы |
| `decision` | сначала требуется продуктовое решение |

Области: `code`, `docs`, `product`, `grant`, `design`, `legal`.
Приоритеты только `P0`, `P1`, `P2`; служебные лейблы — `blocked`, `from-review`.
Новые лейблы, шкалы приоритетов и произвольные статусы не заводить.
Milestone — веха курса; один или ни одного. Не назначай/меняй milestones,
`sveta`, `decision` и не удаляй issues без прямого решения Бориса. В рамках
поручения разрешены обычные задачи `agent`/`human` и исправление явных ошибок
таксономии. Не меняй владельца или смысл чужой задачи молча.

Итерация именуется `SFR-<N>` с темой; имя на доске не означает её запуск.
Постановка и согласованные связанные issues определяют скоуп. Действующую
веху и итерацию бери из текущих решений, не из старых дат или константы скрипта.

## Создание и обновление

Используй установленный `gh`, всегда с явным репозиторием сразу после
подкоманды. Сначала ищи дубли среди открытых и закрытых:

```bash
gh issue list --repo borisboriov/search-for-research --state all --search "ключевые слова"
gh issue view --repo borisboriov/search-for-research 60 --comments
```

Тело: что сделать и границы, откуда задача (ссылка/цитата), нужный контекст,
проверяемый критерий готовности. Связи «часть/блокирует» укажи сразу.
Многострочный текст передавай через `--body-file` с реальными переносами строк.
Результаты и замечания добавляй в существующую issue, если это та же задача.
Находка ревью, исправленная в том же PR, не требует новой issue; самостоятельный
хвост получает `from-review` и полный набор обычных лейблов.

На действующий файл репозитория ссылайся через `blob/main` без номера строки,
раздел называй словами. Для ещё не влитого результата — ссылка на PR;
permalink по SHA нужен при доказательстве конкретной версии. На удалённые
файлы не создавай мёртвые ссылки: имя, цитата и ссылка на историю/источник.
Локальные бинарники называй каноническим именем без пути и персональных данных.

## Передача между сессиями

До PR оставляй в исходной issue компактную запись при смене этапа:
**этап → ветка → чат/сессия (известный адрес) → блокер → следующий шаг**.
Не выдумывай идентификатор чата. После создания PR свяжи его с issue; детали
реализации и ревью веди в PR. Не создавай отдельный handoff-документ.
Запись ссылки на чат не разрешает запускать его или отправлять follow-up:
для этого нужно соответствующее поручение Бориса.

## Закрытие и доска

`Closes #N` в PR/коммите ставь только при выполнении полного DoD к merge.
Наличие слова в истории не означает, что задача выполнена или GitHub её закрыл.
Если остаются выкладка, пользовательская проверка или Drive, используй обычную
связь с PR и оставь задачу открытой. После отдельно разрешённого merge проверь
фактическое закрытие. Отказ от задачи и изменение её скоупа — решение Бориса.

Поля доски производны от issues: Priority — лейбл; закрытое — Done; blocked —
Waiting с учётом приоритета уже выставленного In Progress; остальные — по
правилам `scripts/gh_board_sync.py`. Не проставляй Done ради красивой доски.
Workflow board-sync синхронизирует события issues и делает периодическую сверку;
не дублируй успешную автоматику ручным запуском после каждого комментария.
При расхождении проверь её результат; резерв — `make board-sync-dry`, затем
`make board-sync` в разрешённом скоупе. Нужен доступ `gh` к Projects; сетевую
ошибку не считай причиной повторного login. Если автоматическое поле Iteration
противоречит согласованной работе, зафиксируй расхождение, не объявляй итерацию
открытой и не меняй код синхронизации в рамках обычного триажа.

Для триажа — `make issues-audit`: отчёт только читает и предлагает кандидатов.
Ошибки исправляй в разрешённых границах, похожие заголовки проверяй по содержанию.
Для дайджеста сгруппируй открытые задачи по владельцу, приоритету, блокерам и
подтверждённым срокам. Для закрытия раунда используй `$sfr-close-round`.
