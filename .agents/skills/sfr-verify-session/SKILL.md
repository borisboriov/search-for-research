# Продуктовая проверка SFR

До вердикта — только чтение. Не исправляй код, документы, данные или поля
GitHub, не запускай команды, перезаписывающие артефакты. Отчёт автора —
проверяемые утверждения, не доказательство сам по себе. Приёмка не разрешает merge.

1. Прочитай постановку и последние решения в issues/PR, живой экран
   `docs/product/brief.md`, относящиеся к задаче записи DECISIONS. Для
   эксперимента/техитерации возьми отчёт; для обычной docs-правки — сам документ
   и PR, без требования дополнительного отчёта.
2. Зафиксируй текущую вершину целевой ветки через Git refs API и текущую
   вершину PR; одного `baseRefOid` недостаточно — оно может отставать. Сверь изменённые файлы и фактический
   результат с каждым критерием приёмки; отличай ветку, merge, выкладку и
   проверку пользователями. Проверяй также нарушения границ постановки.
3. Прочитай независимое ревью: кто и что проверил, base/head SHA,
   найденное и исправленное. Финальный комментарий должен подтверждать
   текущую вершину PR. Последующие коммиты требуют проверки нового diff;
   заголовок «Ревью» в отчёте или старое одобрение этого не заменяют.
   Для передачи открытого PR запусти readonly `make handoff-check PR=N`. Цель проверяет
   OPEN, текущие base/head, последний `<!-- sfr-review {...} -->` из
   `$review-iteration` и успешные checks/web/audit. Красный результат блокирует
   передачу PR как готового к merge; зелёный не доказывает качество или
   независимость самого ревью. Такой блокер сам по себе не опровергает
   измерения завершённого эксперимента: оцени их отдельно по пункту 5.
   При проверке уже влитого результата OPEN-gate неприменим: проверь, какая
   версия вошла в merge, её ревью и CI, а затем отдельно факты выкладки и пилота.
4. Сверь CI с актуальной версией PR и её базой: обязательные проверки должны
   завершиться успешно. Старый зелёный запуск, отсутствие check, pending,
   skipped или cancelled не равны успеху. Если workflow проверял синтетический
   merge-коммит, проверь его связь с текущими head/base; не сравнивай его SHA
   с head напрямую. Настройки обязательности checks нельзя выводить только
   из наличия workflow.
5. Проверь численные утверждения по исходным артефактам: метрики, индекс и
   его метаданные, рубрика/судья/набор, отпечатки данных. SQLite открывай
   только для чтения. Success@k сравнивай на неизменном наборе, nDCG разных
   судейских пулов не сопоставляй. Старые Fable и новые astra/max — разные
   оценки. Если заявлена выкладка, нужна её фактическая проверка; отсутствие
   доступа укажи как непроверенный пункт, не как успех.
6. По каждому `Closes #N` проверь полный DoD. Обещанные деплой, пользовательская
   проверка или загрузка Drive, ещё не выполненные, не позволяют закрыть issue
   одним merge. Результаты и текущий статус должны быть согласованы с брифом;
   DECISIONS содержит основания решений, SESSIONS остаётся архивом.

Для эксперимента раздели два вывода:

- **Результат эксперимента:** что подтверждено, опровергнуто или осталось
  неизвестным; выполнено ли поручение и остановлены ли собственные процессы.
  Отрицательный результат может быть полноценным завершением. Независимый
  блокер PR не требует повторять измерения или чинить постороннюю инфраструктуру.
  Если сбой проверки затрагивает достоверность самого эксперимента, результат
  остаётся непроверенным до устранения этой причины.
- **Готовность PR:** актуальные ревью, CI и handoff, оставшиеся блокеры.
  Подтверждённые измерения не заменяют обязательные проверки и разрешение на merge.

Выдай компактную таблицу «требование/утверждение — доказательство — результат»
и отдельно вердикт по PR: **готово к решению о merge / нужны исправления / результат не принят**;
для уже влитого результата — что фактически принято и что ещё не выполнено.
Ошибка в уже опубликованной продуктовой цифре идёт первой. Укажи, что не удалось
проверить, и какие действия нужны до готовности. Ничего не меняй во время этой
проверки: после вердикта продуктовый поток отдельно организует исправления
или синхронизацию по `$sfr-close-round` в рамках разрешённого поручения.
Follow-up техническому чату — только если Борис разрешил его координацию.
Отдельный файл проверки не создавай. При разрешённом сопровождении открытого
PR после вердикта добавь итог с одним маркером:

```text
<!-- sfr-product-review {"base":"<полный base SHA>","head":"<полный head SHA>","verdict":"ready|needs-fixes|blocked"} -->
```

Подставь фактические SHA и ровно один вердикт. `ready` — только после нужной
синхронизации документов и финальной проверки по `$sfr-close-round`;
`needs-fixes` — конкретные исправления в скоупе, `blocked` — недостающее
доказательство, доступ или решение. Новые base/head требуют новой проверки.
Heartbeat при `ready` на тех же base/head не повторяет продуктовую приёмку;
перед следующим действием его актуальные проверки всё равно обязательны.
Для `needs-fixes`/`blocked` повтори проверку после подтверждённого изменения
причины: нового CI, ревью, доказательства или ответа пользователя, даже если
head не изменился. Пока причина та же, не повторяй запись и уведомление.
Маркер относится к готовности PR, не к знаку экспериментального результата.
В тексте рядом укажи отдельный вывод по эксперименту. Не ставь `ready` только
потому, что эксперимент завершён. Завершённое ограниченное поручение может
закончить его мониторинг при `blocked` для PR; сохрани блокер и дальнейшие
действия, не расширяй работу ради зелёного статуса. `$sfr-close-round` применяется
при закрытии всего раунда, а не после каждого измерения.
Маркер не заменяет ревью и не разрешает новый скоуп/merge.
