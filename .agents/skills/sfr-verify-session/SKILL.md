# Продуктовая проверка SFR

До вердикта — только чтение, без исправлений и команд, перезаписывающих
артефакты. Утверждения автора проверяются, приёмка сама не разрешает merge.
Навык применяется к передаваемому результату, не к каждому ответу в обсуждении.

## Содержание и версия

1. Прочитай постановку, последние решения, бриф и относящиеся к задаче
   доказательства. Для техитерации/эксперимента нужен отчёт; для обычной правки
   — изменённый документ. Не требуй дополнительного отчётного файла.
2. Зафиксируй проверяемую версию. Для repo — текущую целевую вершину через
   Git refs API и head PR (`baseRefOid` может отставать); для локального
   оригинала — точный файл, дату/отпечаток и сохранённую предыдущую версию.
   Сверь каждый критерий и границы поручения. Различай ветку, merge,
   выкладку, публикацию Drive и проверку пользователями.
3. Для документов/исследования проверь источники и глубину их проверки,
   выводы, расчёты и допущения, ссылки и сохранность уникальных оснований.
   Принятое, проверенный факт, гипотеза и история различимы; новая редакция
   заменяет прежний текущий текст в своём источнике, не пересказывает его в брифе.
   Локальный результат не требует искусственного PR; статус публикации отдельный.
4. Численные утверждения сверь с исходными артефактами: данные/индекс,
   метаданные, набор, рубрика/судья, отпечатки. SQLite открывай read-only.
   Success@k сравнивай на том же наборе, nDCG разных пулов не сопоставляй;
   Fable и Astra/max — разные оценки. Заявленную выкладку проверяй фактически;
   недоступное доказательство обозначай ограничением, не успехом.
5. По `Closes #N` проверь полный DoD. Невыполненные публикация, деплой или
   пользовательская проверка оставляют задачу открытой. Бриф отражает принятое
   общее состояние, DECISIONS — основания решений, SESSIONS — архив.

Отдельно оцени **результат эксперимента**: что подтверждено, опровергнуто или
неизвестно, выполнено ли поручение и остановлены ли собственные процессы.
Отрицательный результат может завершить эксперимент. Независимый блокер PR
сам по себе не опровергает измерения и не разрешает посторонние исправления;
если сбой затрагивает достоверность результата, он остаётся непроверенным.

## Дополнительно для PR

- Прочитай независимое ревью: автор, диапазон base/head, находки и исправления.
  Последующие коммиты требуют проверки нового diff; заголовок «ревью» и старое
  одобрение не подтверждают текущую версию.
- Для передачи открытого PR выполни readonly `make handoff-check PR=N`:
  OPEN, текущие base/head, последний `sfr-review`, успешные checks/web/audit.
  Красный результат блокирует заявление о готовности PR к merge; зелёный
  не доказывает качество или независимость ревью.
- Проверь CI для текущих head/base, включая родителей синтетического merge.
  Pending, missing, failed, skipped и cancelled не равны успеху. Наличие
  workflow не доказывает серверную обязательность проверки.
- Для влитого результата OPEN-gate неприменим: установи фактическую версию
  merge, её ревью и CI, затем отдельные факты выкладки и пилота.

Подтверждённый результат не заменяет проверки PR. Два вывода — о содержании
и о готовности PR — нельзя сводить в один знак успешности эксперимента.

## Вердикт

Кратко сопоставь требования, доказательства и результат; сначала укажи ошибку
в опубликованном утверждении. Дай вывод по содержанию и оставшимся условиям,
для PR отдельно — **готово к решению о merge / нужны исправления / не готово**.
Для локального артефакта укажи проверенную версию и статус публикации. Отдельный
MD не создавай. Исправления организуются после вердикта в разрешённом scope
по `$sfr-close-round`; сообщения другому чату требуют разрешённой координации.

При разрешённом сопровождении запиши в PR итог с одним маркером:

```text
<!-- sfr-product-review {"base":"<полный base SHA>","head":"<полный head SHA>","verdict":"ready|needs-fixes|blocked"} -->
```

`ready` — только после синхронизации и финальной проверки по `$sfr-close-round`;
`needs-fixes` — конкретные исправления, `blocked` — недостающее доказательство,
доступ или решение. Маркер оценивает PR, не знак результата эксперимента.
Новый base/head требует новой проверки. При прежней версии повторяй её только
после изменения причины блокера (CI, ревью, доказательство, ответ Бориса).
Не дублируй прежний итог/уведомление без изменения фактов; обязательные проверки
перед следующим действием сохраняются. Завершённое ограниченное поручение
может окончиться с явным блокером PR и дальнейшим шагом, без расширения scope.
Маркер не разрешает merge или новую работу.
